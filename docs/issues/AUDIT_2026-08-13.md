## 1. 核心 — なぜデシンクするのか（3系統の結論が一致）

### 一文で

> `netFrame` は「`SceneRunner::Step()` が背圧を通過した回数 + 200」でしかなく、ゲーム側の時計
> （WorldTimer）と**一度も突き合わされていない**。背圧が両者の *番号* だけを D+R 以内に強制的に
> 揃えるため、起動タイミング・FastBoot・ロード時間の差で生じたゲーム状態の食い違いが
> 「番号は合っている」という形で隠蔽され、恒久化する。

### 因果連鎖

```
[T0] NetplaySession.cpp:56   Initialize(200, ...)     ← 各機が「自分のDLL注入時刻」を 200 とする
[T1] SceneRunner.cpp:148-156 FastBoot 中は早期 return  ← (D) メトロノーム待機に到達しない
[T2] NetplaySession.cpp:191  ハンドシェイク中は baseFrame=0
       → SyncCodec.cpp:141 の受信ガードが偽 → ConfirmRemote が一度も呼ばれない
       → SceneRunner.cpp:185 の confirmed = head → lead=0 → 背圧が原理的に無効
[T2'] Metronome は Counting 到達まで Start しない (NetplaySession.cpp:223)
       + TimeHooks が Sleep とゲーム内蔵リミッタを無効化済み (dllmain.cpp:221-222)
       → この窓（最低0.5秒以上）でゲームは無制限FPSでフリーラン、writeHead が暴走
[T3] NetplaySession.cpp:222  Counting 突入時に GetWriteHead() を読むが
       :226 の DebugLog に渡すだけ。★ 唯一の合流点で再基準化していない
[T4] Metronome.cpp:79        catch-up 上限なし → 溜まった債務ぶん無待機で連続実行
[T5] SceneRunner.cpp:184-190 背圧が「番号」だけを D+R 以内に揃える
       → 番号は一致、ゲーム内容は数百フレームずれた状態で固定される
[T6] SceneRunner.cpp:148     FastBoot ゲートは phase<CharaSelect のみ
       → Loading 中も writeHead は加算 → ロード時間差がそのまま状態差に
[T7] 是正機構がすべて不発（下記）
[T8] SceneRunner.cpp:243,249 誤った対応付けのまま両者のゲームメモリへ書き込み
```

### 是正機構が「1つも動いていない」

| 機構 | 状態 | 根拠 |
|---|---|---|
| **IntroBarrier** | **何もブロックしない** | `MatchScene.cpp:130` が `HandleRoundStartSync` の bool 戻り値を捨て、`OnInGame` は void。`SceneRunner.cpp:222` の後、`:236-264` の (F2) が無条件実行。しかも (E) の書込みは**それより前**に完了済み |
| **phaseBaseFrame** | 恒久 0 | `MatchScene.cpp:103` がリテラル 0 を store → `SyncCodec.cpp:183` の `if(>0)` が**到達不能** → `peerPhaseBaseFrame` は書かれも読まれもしない死フィールド |
| **phaseBaseWorldTimer** | 代入のみ | `MatchScene.cpp:100` で代入、読み手は `:105` のログだけ |
| **WorldTimer / RealTimer / RoundTimer** | 算術利用ゼロ | production コードでの用途はログと `MbaaMemTrace` のみ |
| **相手のフレーム番号 `_latestPeerFrame`** | ログのみ | `NetplaySession.cpp:273`。ペース制御にも背圧にも入っていない |
| **α1 補正** | 実質無効 | `alpha1 = max(0, RTT/2 - (D+R)*16666)`。D=2,R=4 なら RTT 200ms 未満で常に 0。かつ両者が同じ値を出すので**相対補正にならない** |
| **`SetRenderSkipByGap(gap)`** | 常に 0 | `SceneRunner.cpp:163` が定数 0 を渡す。gap 追従キャッチアップは死んでいる |

**つまり「同期のための仕掛け」は7つあるが、実際に効いているのは背圧（ハードストップ）1つだけで、
それは番号しか見ていない。**

## 3. 実行環境の結論（Wine 検証）

| 項目 | 結果 |
|---|---|
| サンドボックスの root 権限 | **なし**（`no new privileges`） |
| 32bit ELF ローダ (`/lib/ld-linux.so.2`) | **なし**。i386 multiarch も未設定 |
| Ubuntu アーカイブへの到達 | ✅ 可能。`apt-get download` + `dpkg -x` でユーザ領域に展開できる |
| **mingw32 クロスコンパイル** | ✅ **動作確認済み**。`i686-w64-mingw32-g++` で `d3d9.h`/`dinput.h`/`mmdeviceapi.h` を含む PE32 バイナリの生成に成功。cmake 3.22 も導入済み |
| **Wine で MBAA.exe を動かす** | ❌ **現実的でない**。apt にあるのは wine 6.0.3 の amd64 のみで、32bit exe には `wine32`(i386) が必要。新 WoW64 モード（wine 9.x+）も使えない。i386 ライブラリ群を手動展開してローダを明示指定すれば理論上は動くが、その上で D3D9→OpenGL(llvmpipe) まで揃える必要があり、投資対効果が見合わない |

### 代わりに取るべき道（監査で判明した近道）

harness が**あと少しで Linux ネイティブビルド可能**。harness がリンクする 17 ソースのうち Win32 API に
触れるのは 6 ファイルだけで、残り 11（`FakeGame` / `MatchScene` / `SceneInputFilter` / `NetplayClock` /
`SyncCodec` / `NetplayManager` / `PacketRouter` / `UdpSocket` / `NetworkSimulator` / `PhaseMonitor` /
`GameMemory`）は既にポータブル。`UdpSocket.cpp` は asio standalone のみで winsock 直接使用なし。

| ブロッカー | 対処 |
|---|---|
| `harness/CMakeLists.txt:43` の `ws2_32` 等が `if(WIN32)` の外 | 囲むだけ |
| `MbaaAddresses.hpp:18` の無条件 `#include <windows.h>` | `<cstdint>` で足りる |
| `FrameControl.hpp` / `DirectInputHook.hpp` の `HWND` | `void*` 化か `#ifdef` |
| `IpcData.hpp:82` の `IpcManager` が `_WIN32` 限定なのに `SceneRunner.cpp:335` が無条件呼び出し | seam 化 or no-op |
| `QueryPerformanceCounter` / `Sleep` / `timeBeginPeriod` | `TimeHooks::Real*` が既に薄いラッパなので、そこだけ `std::chrono` に差し替え |
| `WasapiClock.cpp` の COM/WASAPI | 既に QPC フォールバック経路がある（`:139-146`）ので Linux ではそちらだけ残す |
| `UIManager.cpp:17` の `#include <Dbt.h>` | 小文字 `<dbt.h>` へ（case-sensitive FS で唯一失敗する include） |

**見積り 2〜3人日。** これが通れば、harness の2プロセス対戦を Linux で閉ループで回せる。

フレーム空間の一本化を先に済ませ、その上で各機構を1つずつ通電する順序を取る。

## 5. 残る「実機で確認したい」項目

2. `Present` とゲームロジック 1 tick が 1:1 か（`[MEM]` ログの `Δ netFrame / Δ WT` 比で即断できる）
