## C. 実測で確定した「ずれの機構」

### C-1. `WT − netFrame = −156 + starve` （厳密に一致）

| 機体 | 時点 | WT | wh | WT−wh | starve |
|---|---|---|---|---|---|
| host | phase=2 fip=0 | 45 | 201 | −156 | 0 |
| host | phase=2 fip=1740 | 1785 | 1630 | 155 | 311 |
| client | phase=2 fip=1740 | 1785 | 1634 | 151 | 307 |

`(WT−wh) − (−156)` が `starve` と**1フレームの誤差もなく一致**する。
つまり **`starve` の回数がそのまま「netFrame とゲームフレームの対応ずれ量」**であるという
2026-07-27 の結論が、実測で再確認された。

### C-2. ただし今回のずれは 4〜5 フレーム。2026-07 の 363/359 から激減している

キャラセレ終了時点で host starve=311 / client starve=307 → **差は 4**。
`WT−wh` の差も 4 で完全に一致する。

**なぜ改善したかは未特定。** 心当たりは (a) LogSink の非同期化で毎行 fopen が消えフレーム
タイミングの汚染が減った、(b) 入力修正で処理経路が変わった、(c) 単に実行条件の差。
**改善を前提にしないこと。** 機体差・回線劣化がある本番では再び開くはず。

### C-3. 本当に大きいずれは Rematch で生まれている（新発見）

`[IntroBarrier] Both peers reached intro=2!` の記録:

| host BaseWT | 1869 | 5412 |
| client BaseWT | 1870 | **5560** |
| 差 | **1** | **148** |

ラウンド1では1フレームしか違わないのに、**リマッチを挟むと 148 フレーム開く**。

**ずれの主因は starve ではなくメニュー滞在時間の差。** ここは監査で見落としていた。

## D. Phase 1 の設計が確定した — `BaseWT` は既に正しい場所で取れている

C-3 の表は「困った事実」に見えるが、**逆に設計の答えになっている。**

```
[IntroBarrier] Both peers reached intro=2! phaseBaseFrame=0 (WT=5412 BaseWT=5412) Go!
```

`BaseWT` は「**両者が intro=2 に到達したことを相互確認した瞬間の自分の WT**」であり、
これは両機で**同じ論理的瞬間**を指す。だから:

```
relFrame = WT − BaseWT
  host  : 5412 − 5412 = 0
  client: 5560 − 5560 = 0     ← 同じ瞬間が同じ番号になる
```

**BaseWT が両機で違う値（5412 と 5560）であることこそが正しい。** 各自の絶対 WT の差を
吸収するのが基準点の役目だからである。原点を交換・合意する必要すらない。

そして `phaseBaseFrame=0` — 監査が「恒久 0 の死んだフィールド」と指摘したとおり、
**基準は既に採取されているのに、フレーム番号の算出に一度も使われていない。**

### 帰結

| 監査時点の計画 | 実測後の判断 |
|---|---|
| 1-1 Counting 突入時に原点合意 | **不要**（B-3 で原点は揃っている） |
| 1-3 `relFrame = WT − baseWT` | **これが本丸**。B-1/B-2 より前提成立、D で基準点も既存 |
| 1-4 `phaseBaseFrame` を baseWT に転用 | **そのまま実施可**。採取済みの値を配線するだけ |
| ロード中の WT 停止に依存した設計 | **不可**（B-1 で否定）。ただしラウンドごとに基準を取り直すので影響なし |

## E. 今回いちばん危険な発見 — ホストのフリーズが「切断」として検出されない

両ログの末尾:

```
MBAACC_1(host)   : [SyncCodec] RECV pkt: baseFr=5459 …  ← これだけが延々と続く
                   ★ [SceneRunner] も [Backpressure] も止まっている
MBAACC_2(client) : [Backpressure] STALLED head=5459 confirmed=5452 lead=7 maxLead=6 …
                   ★ 延々と繰り返し
```

読み取れること:

1. **ホストのゲームスレッドが完全に停止した**（`Step()` が呼ばれなくなった＝`Present` が来ない）。
   最後の定期ログは `wh=5449 WT=5651 intro=1`。
2. ホストの `writeHead` が 5452 で凍る → クライアントの `confirmed` が 5452 で止まる。
3. クライアントは `lead = 5459 − 5452 = 7 > maxLead 6` で**恒久的に背圧停止**。
   クライアント側もゲームメモリへの書込みが止まり、事実上フリーズする。
4. **`Peer Disconnected` はどちらにも出ていない。**

### なぜ切断にならないか

通信スレッドはゲームスレッドと独立に生きており、`writeHead` が凍っていても
キープアライブを送り続ける。受信側は `_framesSinceLastRecv` がリセットされるので
`alive=1` のまま。つまり:

> **キープアライブは「相手のプロセスが生きている」ことしか示さず、
> 「相手のゲームが進んでいる」ことを一切保証していない。**

片方がフリーズすると、両者が無言で固まり、エラーも出ない。
利用者からは「対戦中に固まった。何も表示されない」としか見えない。

**対処案**: パケットに載っている相手の `baseFrame`（`_latestPeerFrame`。現状ログにしか
使われていない）が一定時間（例: 3秒相当）進まなければ「相手が停止」として扱う。
既にフィールドは流れているので、判定を足すだけで済む。

### ホストが止まった原因は未特定

ログからは `Present` が来なくなったことしか分からない。クラッシュなら DLL のログに何か残る
はずだが、`[FATAL]` も `Aborted` も無い。**利用者が閉じた可能性も否定できない。**
次回の実機テストでは、フリーズしたときにウィンドウが応答するか（描画は止まるが
タイトルバーは動くか）を見てほしい。

### F-1. Rematch の Local/Remote が完全に非対称。自動ナビは一度も動いていない

| | host | client |
|---|---|---|
| `[Rematch] Local selected` | 1 | **0** |
| `[Rematch] Remote selected` | **0** | **506** |
| `[Rematch] Resolved` | 0 | 0 |
| `AutoNav` | 0 | 0 |

- ホストだけが選択し、クライアントは一度も自分で選んでいない
- クライアントはホストの選択を**受信パケットごとに 506 回**適用している（監査 M3 のとおり
  フェーズを見ずにレベル駆動で送られ続けるため）
- `Resolved` が両機 0 ＝ `ResolveMenuSelection()` が一度も成立せず、**自動ナビ機能は死んでいる**

### F-2. ログの 94% がノイズ

`[SyncCodec] RECV pkt`（5267行）と `[Backpressure] NEAR`（5252行）で 11164 行中 10519 行。
毎パケット・毎フレーム出力しており、`[SceneRunner]` の定期ログ 98 行が埋もれる。
LogSink の非同期化で I/O コストは下がったが、**読めないログは無いのと同じ**。
`NEAR` は margin が閾値を下回ったときだけ、`RECV pkt` は異常時だけにすべき。
