# 複数の専用DLLに分割するアキテクチャの評価 (Multi-DLL Approach)

ユーザーからの「機能ごとに細かくDLLを分割し、 물리的な依存関係を切り離すことでAI（および人間）の認知負荷を下げるのはどうか？」というご提案について、非常に鋭く魅力的なアプローチであるため、そのメリット・デメリットと実現可能性を深く検証しました。

## 1. 提案された境界線（Multi-DLL分割アプローチ）

以下のように、各ステートや機能の関心事ごとに別々の `.dll` ファイルをコンパイルし、適宜ゲームプロセス(`MBAA.exe`)にインジェクトしていく構成です。

*   `cccaster_host.exe` (起動・通信管理のみ)
*   **[NEW]** `cccaster_fastboot.dll` (画面遷移・ゲーム起動スキップ専用)
*   **[NEW]** `cccaster_input.dll` (コントローラ入力の読み取りと加工専用)
*   **[NEW]** `cccaster_sync_charaselect.dll` (キャラセレ画面の同期エンジン)
*   **[NEW]** `cccaster_sync_ingame.dll` (対戦中のロールバックエンジン)

## 2. メリット (なぜAIや人間の認知負荷が下がるか)

このアプローチには、まさにソフトウェア工学における「単一責任の原則 (Single Responsibility Principle)」を極限まで押し進めた強力なメリットがあります。

1.  **コンパイルの完全な分離**: `FastBoot` のコードをいじっても、`RollbackEngine` 側の再コンパイルが走りません。依存関係が物理的に遮断されるため、「ある機能の修正が別の機能に追加のバグを生む（デグレ）」リスクをゼロに近づけられます。
2.  **AIの認知負荷の激減**: AI（私）がデバッグや機能追加を行う際、「今は対戦中バグだ、だから `sync_ingame.dll` のフォルダだけ見ればいい」と探索範囲を極小化できます。巨大で複雑な `GameHooks.cpp` を何百行も解析する手間が省けます。
3.  **状態破壊の防止**: キャラセレが終わったら `sync_charaselect.dll` をアンロード（メモリから破棄）してしまえば、メモリリークや意図せぬバックグラウンド処理の暴走をOSレベルで遮断できます。

## 3. デメリットとオーバーヘッド

一方で、複数のDLLを同じプロセス（1つの `MBAA.exe`）に同居させることによる特有の問題も発生します。

1.  **グローバルステートの共有難易度**: 「現在のフレーム数」や「プレイヤーのHPアドレス」など、全フェーズで共通して使いたい情報（シングルトンや静的変数）が、DLLごとに独立（分断）してしまいます。これを解決するには、結局DLL同士を繋ぐための**エクスポート関数渡し（DLL間通信）**が必要になり、インターフェース設計の難易度が跳ね上がります。
2.  **APIフックの競合 (MinHookのバッティング)**: 例えば `FastBoot.dll` と `Input.dll` の両方がDirectXの `Present` (画面描画関数) や `GetDeviceState` (入力取得関数) をフック(横取り)しようとした場合、フックの二重掛けが発生し、順番の制御を誤るとゲームが確定でクラッシュします。
3.  **C++標準ライブラリの肥大化**: MinGWで静的リンク（`-static`）している場合、各DLLにそれぞれ C++ 標準ライブラリが丸ごと組み込まれるため、生成されるファイルの合計サイズが巨大になり、ビルド時間も伸びる可能性があります。

## 4. 結論と折衷案の提案

DLLを機能単位に分けるという思想は**アーキテクチャとして大正解**です。しかし、物理的な `.dll` ファイル自体を複数に分けて `MBAA.exe` に複数回インジェクトする方式は、フックAPIの競合やDLL間通信の実装コストが高く、かえってバグの温床（認知負荷の増大）になりかねません。

**【推奨する折衷アプローチ：論理的分離 (Static Library化)】**

「DLLは1つ (`cccaster_hook.dll`) のままにするが、CMake（ビルドシステム）とフォルダ構成において完全にモジュールを独立させる（静的ライブラリ化する）」という方法を提案します。

CMakeLists.txt 上で以下のように分離します。
*   `lib_fastboot.a` (画面遷移モジュール)
*   `lib_input.a` (入力モジュール)
*   `lib_sync_engine.a` (各種同期モジュール)

これらは互いのヘッダ（依存）を一切持たず、最終的に `cccaster_hook.dll` が「司令塔」としてこれらをリンクし、一度だけゲームにインジェクトします。

*   **メリット:**
    *   物理的なファイル構造とCMakeスコープは分離されるため、AIの認知負荷は下がる（目的のフォルダしか見なくて済む）。
    *   APIフックの競合が起きない（司令塔が1箇所でフックを一括管理できる）。
    *   グローバル変数の共有が簡単。

**ユーザーの目指す「見通しの良さ（認知負荷の低減）」は、この「論理的なモジュール分割（Static Library分割）」の手法で、オーバーヘッドの落とし穴を避けつつ完全に達成可能です。** 次のステップでは、まず現状の巨大なコードベースをこれらの独立したモジュール(`lib`)にリファクタリングして切り離す作業から始めるのが最善と考えます。
