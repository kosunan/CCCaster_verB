# UDP通信データを直接DLL（カーネル）で受け取るアプローチ

ユーザーからのご指摘「プロセス間通信（IPC）のパケットリレーのオーバーヘッドを無くすために、DLL側で直接カーネルから通信データ（UDP）を受け取れないか？」に対する回答設計です。結論から言うと**可能であり、かつ非常に美しい（低遅延な）アプローチ**です。

現在のアーキテクチャ（これ以上コンポーネントを肥大化させず、安定したコードを維持する方針）を守りながら、通信の受信だけをDLLに直接やらせるための実装方法を2つ検討しました。

## 検討案1: ソケット複写 (WSADuplicateSocket) の利用
呼び出しホスト (`CCCaster_v10.exe`) が生成してP2P接続を確立した UDP ソケット（WinSockの `SOCKET` ハンドル）を、Windows APIの `WSADuplicateSocket` を用いて、インジェクトした先のゲームプロセス (`MBAA.exe` / DLL) に丸ごと複製・譲渡します。
*   **メリット:** 呼び出しホストで確立した完璧な接続状態をそのまま引き継げるため、IPの整合性がとれる。
*   **デメリット:** ASIO（現在使用している非同期ライブラリ）の `io_context` の奥深くに秘匿されているネイティブハンドルを無理やり引っこ抜き、さらにプロセスを越えて再構築する処理は非常に黒魔術的であり、**デグレ（既存の通信が壊れるバグ）を引き起こすリスクが極めて高い**です。

## 検討案2: 接続先情報のみを渡し、DLL側で別ポートを開く (セーフ・アプローチ)
呼び出しホストからは「接続相手（通信相手）のIPアドレス」や「ポート番号」だけを共有メモリ経由等で渡します。そして、インジェクトされた直後のDLL内の `GameHooks::Initialize()` において、**DLL独自に `recvfrom` を叩く専用のUDP受信用スレッド（別ポート）を立ち上げます。**
*   **メリット:** 現在の呼び出しホスト側のASIO通信網を **1ミリも改変せず** に済みます。既存の機能は完全に無傷（デグレリスク0）です。
*   **デメリット:** 対戦相手と通信するためのUDPポートが、呼び出しホスト用とDLL用の2つ必要になります（ただしUDPはコネクションレスなので、通信ポートの一時切断・同ポートでの開き直しで回避可能）。

## 採用する方針 (同ポート再バインド・アプローチ)

最も安全に、かつ「最適化せずそのまま進めたい」という方針に合致するのは **案2（接続情報の受け渡しによるDLL上での直接受信）** を応用し、**同じポート番号を使い回す手法** です。

1.  **呼び出しホストの役割:** 通信相手（通信クライアント/通信ホストを問わず）とのP2Pの確立処理（Ping交換やハンドシェイク）を終えるまで担当する。
2.  **ゲーム起動直前:** 呼び出しホストのロジックは **明示的にUDPソケットを閉じる（`socket.close()`）**。
3.  **DLL側 (`cccaster_hook.dll`) の役割:** インジェクトされた直後、呼び出しホストが手放したのと同じポート番号で `bind()` して待ち受ける。
4.  これで、通信相手から送られてくるキャラセレや対戦中のパケットは、通信が途切れることなく全てカーネルから**直接DLL（ゲームプロセス内）に着弾**します。

### 次のアクション

この「通信ソケット待受のバトンタッチ（呼び出しホスト -> DLL）」手法を使えば、呼び出しホスト側からDLL側への面倒な共有メモリ(IPC)パケットリレーを実装する手間が省け、かつオーバーヘッドゼロでDLLが直接パケットを読み取れるようになります。

この方針で `CliMenu.cpp` (Host側のソケットの一時停止) と `GameHooks.cpp` (DLL側の受信用ソケットの再バインド) の実装を進めてよろしいでしょうか？
