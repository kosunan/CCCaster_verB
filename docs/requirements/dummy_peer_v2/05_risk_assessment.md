## 3. 各リスクの詳細

---

### リスク1: 入力パケットの仕様未確定（2B vs 51B）

**発見元**: 両レポート共通  
**影響度**: 🔴 致命的 — パケットフォーマットが全コンポーネントの設計に波及  
**緊急度**: 🔴 即時 — これを決めないと送信側の実装に着手できない

**現状**:
- DLLは入力を**受信するだけ**で送信コードが存在しない
- 受信側は `PacketRouter` の `data.size() == 2` ハードコードで判定
- `RedundantProtocol` (51B, CCTR冗長パケット) は定義済みだが未接続

**選択肢**:

| 選択肢 | メリット | デメリット |
|---|---|---|
| A: 2バイトのまま進む | 実装が最小限、DummyPeer互換維持 | `frameId` なし→ロールバック不可 |
| B: 51B冗長パケットに移行 | ロールバック・パケロス復旧が可能 | PacketRouter改修が必須、帯域増加 |
| C: 新ヘッダ設計で作り直し | 将来拡張に最適 | 工数が最大、既存コードの大改修 |

> [!CAUTION]
> **選択肢Aは本番運用では機能不全**。ロールバックの根幹機能が動作しない。最低でも `frameId` を含むフォーマットが必要。

---

### リスク2: PacketRouter の拡張性不足

**発見元**: 04_packet_analysis_report.md §5 WARNING  
**影響度**: 🔴 致命的 — 新パケット種別を追加するたびに改修が必要  
**緊急度**: 🟡 中期 — パケット仕様確定後に着手可能

**現状**:
```
PacketRouter::OnPacket() の分岐:
├─ data[0] == 0x10-0x12 → TimeSynchronizer  (先頭バイト判定)
├─ data.size() == 2     → 入力パケット      (サイズ判定)
└─ それ以外             → UNKNOWN ログ
```

**問題**: CCTRパケット(51B)、メニュー同期、ロード同期など新種別を追加する際、**判定条件が衝突する可能性**がある。特にCCTRパケットは先頭4バイトがマジックナンバーであり、現在の「先頭バイト判定」とは共存できない。

**対策案**: マジックナンバー `0x42525443` ("CCTR") の有無を最優先で判定し、TimeSync (0x10-0x12) と旧2Bパケットは後方互換として残す3段判定を導入。

### リスク3: RedundantProtocol の進退問題

**発見元**: packet_analysis.md §3-A  
**影響度**: 🟡 重大 — 使うにも捨てるにも判断が必要  
**緊急度**: 🟡 中期

**現状**:
- `EncodeInput` / `DecodeInput` は実装済み (計95行)
- Scene層からもPacketRouterからも**一切呼ばれていない**
- `creationTimeUs` は0固定（モック実装）

**選択肢**:

| 選択肢 | 工数 | リスク |
|---|---|---|
| A: そのまま接続する | 小 | モック部分の修正が必要、設計が最適か不明 |
| B: 必要フィールドだけ抽出して新設計 | 中 | 二重管理のリスク |
| C: 完全削除して作り直し | 大 | 投入済み工数の無駄 |

### リスク4: frameId 不在によるロールバック不全

**発見元**: 両レポート共通  
**影響度**: 🔴 致命的 — ロールバックネットコードの根幹  
**緊急度**: 🔴 即時

**現状**:
- 現行の2バイト入力パケットには `frameId` が含まれない
- `s_latestRemoteInput` (atomic uint16_t) は「最新の値」を上書きするだけ
- **フレーム番号なしでは「どのフレームの入力か」を特定できない**

**影響シナリオ**:
```
Frame 10 の入力パケットがネットワーク遅延で Frame 12 に到着
→ frameId がないため Frame 12 の入力として処理される
→ ロールバックが正しい位置に戻れない
→ ゲーム状態がデシンクする
```

> [!CAUTION]
> DummyPeerテストでは遅延がほぼ0のため顕在化しないが、**実ネットワーク環境では100%問題になる**。

### リスク6: Phase 2 相対補正の未接続

**発見元**: packet_analysis.md §5 🟡推奨  
**影響度**: 🟡 重大 — 長時間対戦の品質に直結  
**緊急度**: 🟢 長期

**現状**:
- `TimeSynchronizer::OnReceivePeerClockReport()` は定義済み
- 入力パケットに `wasapiClock` を付加して送る仕組みが未接続
- `RedundantProtocol.InputPacket` には `wasapiClock` フィールドが存在

**影響**: WASAPIクロックの微小ドリフト (数PPM) が10分間で数msのズレとして蓄積し、ロールバック頻度が上昇する。**テスト環境（数分）では見えないが、ランクマッチ（10-30分）で体感悪化する**。

---

### リスク7: プロトコルバージョン交換の欠如

**発見元**: Negotiation ↔ TimeSync の境界分析  
**影響度**: 🟢 軽微 — 現時点ではユーザーが1バージョンしか使わない  
**緊急度**: 🟢 長期

**現状**: Negotiation (26B) と TimeSync (0x10-0x12) の間にバージョンハンドシェイクがない。将来パケットフォーマットを変更した際、**旧バージョンのクライアントと新バージョンのホストが接続すると無言で壊れる**。

---

### リスク8: パケロス復旧ロジックの未実装

**発見元**: packet_analysis.md §3-A / RedundantProtocol 設計  
**影響度**: 🟡 重大 — WiFi環境やVPN経由で問題化  
**緊急度**: 🟡 中期

**現状**:
- `historyInputs[10]` （過去10フレーム分の入力）はエンコード済み
- **受信側で「パケロス検出 → historyInputsから補完」するロジックが存在しない**
- 1パケット落ちるたびにロールバックが必要になる

**対策**: 受信側で `frameId` の連続性を監視し、欠番を `historyInputs` から復元する処理が必要。

---

### リスク9: TimeHooks 1000倍速のTimeSync干渉

**発見元**: TimeHooks統合分析  
**影響度**: 🟡 重大  
**緊急度**: 🔴 即時 — 現在のコードで既に発生しうる

**現状**:
- `MbaaSpeedController` が全SpeedModeで `SetTimeMultiplier(1000)` を呼ぶ
- `TimeSynchronizer` は `RealSleep` / `RealQPC` に差し替え済み
- **しかし `TimeSynchronizer::GetLocalTimeUs()` 内の QPC はまだ差し替え漏れの可能性がある**

**最悪シナリオ**:
```
PING_INTERVAL_US = 50,000μs (50ms)
→ TimeHooksで1000倍速 → GetLocalTimeUs()が1000倍速の時刻を返す
→ 50ms のはずが 0.05ms 間隔で SYNC_REQ が10回送信
→ θ計測がすべて同一タイミングのサンプルになり精度崩壊
```

> [!WARNING]
> `TimeSynchronizer.cpp` の `GetLocalTimeUs()` 内で `QueryPerformanceCounter` が `RealQPC` に差し替えられたか再確認が必要。

---

### リスク10: 片方向通信テストの偽の安心感

**発見元**: 04_packet_analysis_report.md §6  
**影響度**: 🔴 致命的 — テスト結果の信頼性に直結  
**緊急度**: 🔴 即時

**現状**:
```
DummyPeer → DLL:  2B入力パケット      ★ 動作中
DLL → DummyPeer:  入力パケット送信     ❌ 未実装
```

**問題**: 「テストが通った」=「本番で動く」という錯覚が生まれる。実際には:
- UDP NAT ホールパンチングの双方向性が未検証
- ポート開放の片方向問題が検出不能
- 双方向パケロスの耐性が未評価
- DLL側の送信タイミング（60FPSループとの同期）が設計されていない
