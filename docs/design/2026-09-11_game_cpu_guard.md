# GPU割込みとゲームスレッドのCPU競合を避ける

## 実装

ネット対戦のゲームスレッドについて、CPU0と同じ物理コアの論理CPUを実行候補から除外する。このPCではCPU0/1を外し、maskはffff→fffc。SMTの相手もトポロジーAPIから求め、CPU1と固定的に仮定しない。

対象は単一processor group・32論理CPU以下・4物理コア以上。トポロジー不明や移動先なしの場合は変更しない。初期のprocess/threadの許可範囲から選び、後から狭められたprocess/threadの範囲も広げない。

`TimingThread("game")` で設定し、`SceneRunner::Step` の準備先頭で配置を確認する。CPU0側へ戻されていた場合だけ再適用する。スピンループ内にAPI呼出しを追加しない。対象スレッドの終了時に、変更前のmaskへ復帰する。

入力採取スレッド、WASAPI worker、更新締切、ロールバック処理、GPU描画命令は変更しない。プロセス全体のaffinity、IRQ設定、ドライバ設定も変更しない。

既定で有効。起動前に `CCCASTER_DISABLE_GAME_CPU_GUARD=1` を指定すれば従来配置へ戻せる。適用・再適用・エラーはGameCpuGuard/GameCpuGuardRestoreに記録。別PCでの効果は未確認。

## 比較から修正した点

起動時に一度だけ設定する版は失敗した。`bounded_real_20260911_064228` / `spin_etw_20260911_064224` で対策側もCPU0へ戻り、GPU割込みを受けていた。1398確定Fは一致したが、監視空白の最大354.3µs、終了遅れ最大188.933µsであり、この版を対策完了とはしていない。

現在の実装ではMMCSS登録後の最初のStepでffffへの復帰を検出してfffcへ再適用した。その後も準備時に監視する。初回のAPI順序はaffinity→MMCSS登録→Maintainなので、D3Dが戻したと断定できない。登録等の外部APIで配置が変わることに対応した。

独立レビューで、再適用時に現在のthread maskを交差して動的制約を保護し、初期状態が既に除外済みでも維持対象へ登録するよう修正した。

入力採取ログはクライアント131079FのREPHASE直後に前値保持1回あり、初回ロールバック131378Fより前。通常戦闘集計内の保持通知は0。自動入力試験であり、実コントローラの体感確認は今回行っていない。既存GUI/CLI待受プロセスは維持し、今回起動したゲーム・採取だけを終了した。

32bitビルドと19 C++テスト成功。CPU0物理コア/SMTの除外、既存許可範囲の維持、候補なし、32bit非対応構成の無変更をテストした。

この対策はドライバの処理量を減らさず、ゲームがその割込みCPUを使わないようにする。別CPUの割込み、OSのスケジューリング、終了後処理の外れ値、準備超過までは解消しない。4コア未満・多group・ハイブリッドCPU等の別構成の性能は未確認。

根拠仕様: [SetThreadAffinityMask](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadaffinitymask)。実機の効果は上記ETWとゲームログに基づく。
