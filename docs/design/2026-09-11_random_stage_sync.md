# ランダムステージの抽選結果を同期する

対象: MBAACC Ver.1.07 Rev.1.4.0、32bit。Steam側は別管理。

## 原因と修正

独立キャラセレでは `0x42725B` のステージ決定戻り値255を観測し、`0x74FD98` を最終ステージとして交換していた。しかし0はランダム指定であり、実ステージではない。ゲームはその後 `0x42F00D` で0を検査し、`0x42F016` から `0x42F140` を呼んで抽選する。両端の独立操作中の乱数状態は同一ではないため、0で合意しても別々の背景をロードする。戦闘入口のRNG合流より前に背景が決まるため、その合流では直らない。

ホストの決定時、0の場合だけ元ゲームの `0x42F140` を一度呼び、実ステージ番号を既存の改訂番号・ACK経路で交換する。元ゲームの使用可能ステージと除外設定を維持し、独自の候補リストは作らない。両者は受信確認後に非0の実番号を使ってロードするため再抽選されない。ゲームスレッドで処理し、版識別に加えて抽選関数入口の命令列も照合する。確定通知のstage=0は不正として拒否する。

通信形式は版10・拡張2のまま。旧ホストの未解決ランダム通知は拒否されるため、両者とも今回のDLLへ更新する。

## 再現と検証

`CCCASTER_SCRIPT_INPUT=1` と `CCCASTER_TEST_RANDOM_STAGE=1` のときだけ、両キャラ確定後にゲームスレッドからランダムのselector=0を設定し、専用入力時計の通常決定入力で選択する。手操作・実コントローラ試験とは区別する。

- 修正前 `build_logs/bounded_real_20260911_153602`：60〜96ms・損失5%、双方COMMIT=0、LOADEDはホスト25／クライアント7。比較器は不一致を検出。
- 修正後 `build_logs/bounded_real_20260911_153716`：同ラグ＋クライアント7秒無操作、ホストのみ1回抽選。双方COMMIT/LOADED=40。963確定FのREC/FRAME/STATE/MEM差分・欠落・失敗0。選択比較は合格。戦闘比較器の1000F下限に足りないため、全体判定falseを保持し、試験時間を45秒に延長して再確認する。
- 32bit Releaseビルド、22 CTest成功。通信テストに未確定0の許可、確定0の拒否、1〜99の上限、不正値で既存状態を上書きしない確認を追加。
- 最終ランダム試験 `build_logs/bounded_real_20260911_153805`：45秒、60〜96ms・損失5%・クライアント7秒無操作、D2/R4。ホストのみ抽選1回、双方COMMIT/LOADED=1。1264確定FのREC/FRAME/STATE/MEM差分・欠落・失敗0、ロールバック377/385回、最大深度4。選択・戦闘比較とも合格。`selection_result.json` と `rollback_comparison.json` が根拠。
- 通常の自動入力列 `build_logs/bounded_real_20260911_153903`：35秒、同ラグ、専用ランダム指定なし。この入力列でもランダムが選ばれ、双方COMMIT/LOADED=38で一致、932確定F差分・欠落・失敗0。選択比較は合格、戦闘比較の1000F下限未満によるfalseは保持。この回を固定ステージ選択の検証とは扱わない。

両テストコピーへ修正DLLを反映し、ビルド出力とのSHA256一致を確認した。`B6F8DB84FBF3D29C27C1200928750CCBAD45C134B644D2743184EC6807FA7C2B`。CLI/DLLのPE Machineはいずれも0x014c。テストルート配下55 INIのSHA256は作業前と一致（`build_logs/random_stage_ini_before.json`）。既存ゲームプロセスはなく、今回起動したゲーム／ランチャーだけを終了した。

`verify_selection_pair.py --random-stage` は、両者の確定／ロード値一致に加え、ホストの抽選が各選択で1回だけ、クライアントで抽選しないこと、抽選結果が非0の実番号であることを検査する。

別PC・実コントローラ・全ステージ設定・再戦からキャラセレの反復は未確認。
