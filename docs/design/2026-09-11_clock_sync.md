# 相手時計の予測と入力メトロノーム同期（2026-09-11）

通信版8。双方のEXEとDLLを同時に更新する。

## 実装

4時刻の往復観測から時計差を求め、直近30観測の最小RTTを採用。同RTTでは新しい観測を優先する。8秒分を1秒単位にまとめ、低RTT観測の傾きから時計の周波数差を推定する。推定は±250ppm、外挿は±2秒に制限する。回線の往復非対称性はこの情報だけでは分離できず、絶対的な同期精度は保証できない。

パケットに次の入力フレーム番号とWASAPI締切を追加。ホストを共通基準とし、クライアントは相手の締切を自分の時計へ変換する。同じ画面世代で250ms以内の新しい情報だけを使用する。1F未満の差は1回最大250usの補正、1F以上は1回最大100msの即時補正。両者が相互に追いかける振動を避けるためホスト側の時計は追従させない。

ゲームが入力時計より1Fでも遅れれば通常の待機を省略し、中央バッファを順に消費して追いつく。フレーム番号や保存済み入力は飛ばさない。処理時間そのものは消せないため、ゲームが持続的に60fps未満なら追いつけない。採取スレッドまで停止した過去の操作は復元できず、欠けた枠には直前値を保持する。

入力採取の待機は高解像度waitable timerと最後の約100usの締切確認へ変更。16,666usの端数は通常速度で累積補正し60回で1秒とする。WASAPIは時刻基準、waitable timerはCPUを返す待機手段であり、役割は異なる。

Sleep/QPC/GetTickCount/timeGetTimeはMBAA.exeのインポート表だけを差し替える。DLLやオーディオ側のAPIをプロセス全体で差し替える方式を撤去した。ゲーム内蔵リミッタを回避する仮想時間加速は残る。ゲームのフレーム制御関数そのものを直接置換する方式は今回実装していない。

IAudioClockの手書きGUIDがSDKの値と違っており、従来はWASAPI初期化に失敗してQPCへフォールバックしていた。SDK定義へ統一し、周波数取得の成功も確認するよう修正。今回のベンチマークはWASAPI=1を確認した。音声機器が利用できない場合は引き続きQPCを使用する。

## 検証

Release 32bitビルド成功、既存を含む11テスト成功。

実WASAPIを使う各120フレームの単独待機測定（us、締切に対する遅れ）:

|方式|中央値|95%点|最大|
|---|---:|---:|---:|
|従来Sleep(1)|887|1928|1998|
|高精度待機|120|405|496|

この数値は当PCでの短時間の待機測定であり、相手との同期誤差や実対戦中の最悪遅延を表さない。Windowsのスケジューラ、ドライバー、負荷により遅延は増えうる。

実ゲーム40秒、ネットワーク試験設定15,25,5。ログ: build_logs/bounded_real_20260911_011052。比較対象の確定1086フレームで入力・FRAME・STATE・MEMの不一致0、欠落0、失敗ログ0。ロールバックはホスト194回/クライアント137回、最大深度3/4。ロールアップ中央値2141.5/1908us、最大5281/6594us。絶対WorldTimerとメニューカウンタは既存比較器の除外項目。

クライアントの補正ログは+47996us、+34610us、-18593us。最後の補正で欠けた1入力枠は前回値を保持した。実WANの非対称経路や長時間ドリフト、意図的な長時間ゲーム停止の試験は行っていない。全ケースの実機確認まで完了したという意味ではない。
