# ウィンドウ移動後の描画停止の切り分け

## 申告と変更範囲

時計追従変更後、検証中の2窓でタイトルバーを移動した後、操作していない間にも描画OFFが数秒続くとの申告があった。

今回のソース変更は `WndProcHook` の追加診断だけ。`CCCASTER_CLOCK_FOLLOW_TRACE=1` のとき、`WM_ENTERSIZEMOVE/WM_EXITSIZEMOVE` を `[WindowMove]` として実QPC ticks・適用F・採取Fとともに記録する。従来のWndProc処理はそのまま通す。時計追従・補正量・入力採取・予測上限・描画省略条件を変更していない。**症状を修正したと認定しない。**

## 前回ログとの対応

申告の対象は別起動の対戦ではなく、こちらの検証で起動した2窓とユーザーに確認した。前回最終の再戦試験には約465/702msの停止があり、その直後は1F約0.2〜0.7msで入力を消費していた。ホストの約476msという再計算時間には操作による停止が含まれる可能性があり、純粋な再計算コストと断定できない。

同試験では相手時計モデルが未採用で、速度・位相補正は0、大差復帰REPHASEも0。`CCCASTER_TEST_RETRY_QUICK` によって各戦闘世代600F以降に残り時間を1へ設定し、再戦画面と双方ONCE待機を短時間で通していた。申告された不定期停止とこの試験用遷移が重なった可能性はあるが、原因確定ではない。

原ログを `build_logs/window_drag_20260912/user_game_1.log`、`user_game_2.log` へ退避した。前回の通常更新周期の最大値は実測ではあるものの、操作の影響を含むため、無操作時の性能比較には用いない。

## 低遅延でのユーザー操作

同一PC2窓、210秒、D2/R4、TimeScale1、自動入力、疑似受信遅延15〜25ms・損失5%。強制時間切れ・再戦短縮なし。ClockFollow/UpdateCadence/FrameTimingの計測ON。ユーザーが同じ移動操作を行い、**正常復帰**と回答した。

| 項目 | ホスト | クライアント |
| --- | ---: | ---: |
| 終了まで記録できた移動操作 | 13回 | 17回 |
| 通常入力の追いつき区間 | 5 | 16 |
| 最大入力残数 | 159F | 85F |
| 追いつき開始→次の通常更新の最大 | 63.7934ms | 53.8684ms |
| 大差復帰 REPHASE | 0 | 0 |

10,111確定Fの入力・代表状態・保存領域比較が一致し、差分・欠落・同期失敗0。両側WASAPI active。クライアントの時計モデル採用後も移動操作を含めて確認した。入力残数は採取済みFとゲームが消費するFの差であり、ロールバックの深さとは別。

追いつき所要時間は、連続した `InputCatchup` の最初のFから、その次の描画省略しない通常Fまでを `UpdateCadence` の実QPC ticksで対応づけた値。移動中に止まっていた時間を含まない。GPUによる実表示の完了時刻や、全ての画面遷移の所要時間ではない。

根拠: `build_logs/window_drag_20260912/reproduce_low/` のゲームログ、`rollback_comparison.json`、`recovery_analysis.json`。集計スクリプトは同作業フォルダーの `analyze_recovery.py`。

## 追加試行と残る範囲

最初のComputer Use試行では短い実ドラッグの後、システムメニューからの移動モードを長時間保持してしまい、入力待ちの3秒期限切れで終了した。入力保持には有限の上限があり、この試行を正常復帰の根拠にはしない。ログは `build_logs/window_drag_20260912/reproduce/`。ユーザーの通常操作試験とは区別する。

診断追加後の32bitビルドと32 CTestに成功。元の秒単位の不定期停止は、この低遅延条件では再現していない。

## ユーザー指定の高遅延再現試験

続けてユーザーの依頼で疑似受信遅延60〜96ms・損失5%へ変更し、同じ210秒で確認した。D2/R4、自動入力、WASAPI、診断設定は同じ。強制時間切れ・再戦短縮・近距離再ヒット負荷は無効。ユーザーがタイトルバーを操作し、こちらも**正常復帰**と回答した。

| 項目 | ホスト | クライアント |
| --- | ---: | ---: |
| 移動操作 | 6回 | 7回 |
| 最長の移動停止 | 470.4544ms | 2484.4045ms |
| 通常入力の追いつき区間 | 9 | 9 |
| 最大入力残数 | 33F | 152F |
| 追いつき開始→次の通常更新の最大 | 8.8019ms | 50.4837ms |
| ロールバック回数 | 3921 | 3932 |
| 大差復帰 REPHASE | 0 | 0 |

10,528確定Fの比較一致、差分・欠落・同期失敗0。双方WASAPI activeでQPC切替なし。高遅延下では時計モデルが未採用のまま学習を継続し、微差補正は無効だった。従って、雑音下で採用されたモデルの故障耐性まで確認した試験ではない。ロールバックの回数が多いことと、描画OFFが秒単位で連続することは区別する。

根拠: `build_logs/window_drag_20260912/user_high/` のゲームログ、`rollback_comparison.json`、`recovery_analysis.json`。13回の移動操作で当初の不定期停止は再現しなかった。原因は未確定で、追従設定を変更した修正版という扱いにはしない。

低遅延・高遅延とも同一の診断追加DLLを使用し、両テストコピーへ反映済み。今回起動したゲームは終了。保全対象30ファイル（28 INIと2ゲームEXE）はSHA256不変。`manifest.json` にDLLと変更ソースのSHA256を保存した。
