# 初回起動を約1.69秒短縮する

## 結果と測定条件

対象はMBAACC Ver.1.07 Rev.1.4.0（32bit）。今回の依頼は単独で実装・確認した。前回のDDSキャッシュ方式に対し、キャッシュ未作成の初回でも短縮する。

同一PCでbaseline→fastを交互に各3回。毎回独立した未作成のアプリ用キャッシュを指定し、既存キャッシュを使用しない。Windowsのファイルキャッシュは消去していないため、OS再起動直後やストレージの完全な冷起動とは区別する。TrainingはGUI workerの起動要求から、Versusは同一PCのCLI 2窓の最初の起動要求から両側が準備完了するまで。GUIのクリック自体からの時間、別PC/WANは未測定。

| モード | 従来の初回・中央値 | 今回・中央値 | 短縮 | 従来の範囲 | 今回の範囲 |
|---|---:|---:|---:|---:|---:|
| トレーニング | 3.445秒 | 1.758秒 | **1.686秒** | 3.387～3.541秒 | 1.754～1.862秒 |
| プレイヤー対戦・両側 | 4.575秒 | 2.877秒 | **1.698秒** | 4.557～5.290秒 | 2.803～2.981秒 |

入力経路到達・正しいゲームモード・成功したPresentをすべて検出し、その後2秒維持。12/12試行成功。PresentはAPI上の表示要求であり、物理ディスプレイの応答時間ではない。

正式集計: `build_logs/startup_first_20260912/release/summary.json` と `summary.txt`。同フォルダーの `final_{training,versus}_{baseline,fast}_{1,2,3}/result.json` に起動時刻・全イベント・EXE/DLL SHA256・終了状態を保存。上位フォルダーの旧 `final_*` は途中のパディングDDS API版であり、この表には含めない。タイトル遷移を変えた途中試験も `title_final_*` に分離している。

## 逆アセンブルと変更

`0x4BD328 → 0x4DE5D2` のD3DXGetImageInfoが入力素材の情報を求め、その後 `0x4BD3F2 → 0x4DE5CC` がD3DXCreateTextureFromFileInMemoryExを呼ぶ。たとえば640×480のDXT2素材が1024×512テクスチャとなる。フィルタなしでも元のAPIが圧縮ブロックを復号・再圧縮するため、コピーで足りる処理に時間がかかっていた。前回方式はこの結果をファイル化するので初回には効果がない。

- 既知ヘッダー・単一mip・DXT1～5・寸法・元画像情報・API引数を照合した素材だけ、必要寸法のMANAGEDテクスチャを作成し、圧縮ブロックを行単位で転送。右端と下端の余白をゼロにする。寸法・形式・mip数とLockRectのpitchを確認し、生成や照合の失敗・対象外形式は元APIへ戻す。
- 原画像の情報は呼出し直前の値を維持する。素材の準備を戦闘中へ先送りせず、キャラクター選択到達時にCALLを書き戻す。初回フレーム後の追加素材にも適用するため、対象は135枚から296枚に増えた。対象外の156呼出しは元APIで準備する。
- 既定経路はキャッシュの読込み・ハッシュ生成・書込みを行わない。旧 `startup-textures-v2` は削除せず保持し、明示的な比較用 `CCCASTER_STARTUP_FIRST_BASELINE=1` の時だけ従来経路を使う。
- 実D3Dデバイス生成後、画像初期化と並行してDirectInputの作成とデバイス一覧取得だけを行う。再帰mutexで通常Initializeへ引き継ぎ、ゲームスレッド上でデバイスをウィンドウへ関連付け、設定を反映する。初回成功後は再列挙しない。ワーカー生成失敗時は従来の同期初期化へ戻し、ワーカー中はDLL参照を保持する。
- 診断1回では入力準備約142.5msを画像準備中へ移し、ゲームスレッドの初期化は0.156ms。正式Training fastの一例は先行125.5ms、最終初期化0.123ms。入力受付前に初期化完了を待つ。

メモリ上のCALL差替えは既存の対象EXE照合と命令・分岐先照合の下で行い、終了時に復元する。EXEファイル自体は書き換えない。通常の3→2→25→20遷移は維持し、試したタイトル飛越しは短縮効果が乏しく採用しなかった。ゲーム状態や派生入力への直接書込み、`CC_SKIP_FRAMES_ADDR`への書込みは追加していない。

## 画像の同一性と制限

`CCCASTER_STARTUP_ASSETS_VERIFY=1` の `upload_verify/game_1.log` で296/296テクスチャをLockRectで読み返し、元素材の全圧縮ブロックとゼロ余白の一致を確認した。拒否0。実装は正式版と同じDirectDds関数で、入力先行列挙を追加する前の画像検証である。

従来APIの生成物との完全一致は204枚、不一致は92枚。**従来の再圧縮後画像との画素完全一致は主張しない。** 新方式は元素材を再圧縮せず保持する。初期135枚中の不一致38枚についてソフトウェア復号した参考比較では、変化159,937画素、RGB最大差16/255、alpha差0。これは92枚全体の上限や実ディスプレイ上の測定ではない。`dds_delta.json` と `src/harness/analyze_dds_delta.py` に根拠を保存した。

全キャラクター・全演出・別GPUでの描画互換性、物理コントローラの全機種、低速ディスク・OS冷起動は未確認。現在の入力時計・通信版10/拡張5・60Hz締切・ロールバック方式は維持する。既存課題の全通常F±3µs達成とは別の検証である。

## 最終検証と反映

- `build_logs/regression_20260912_200136_630673/summary.json`: 32bitビルド、29 CTest、67 Python試験、同期harness成功。quick profileであり、既知の全F±3µs課題を含むreal profile合格とは主張しない。
- `build_logs/virtual_pad_20260912_195826/`: 90秒、遅延15～25ms・損失5%。ViGEm DS4→通常DirectInput→入力時計で方向・ボタン・左右分離26項目成功。ランダムステージと双方ONCE再戦に成功し、1995確定FのREC/FRAME/STATE/MEM比較は差分・欠落0。物理パッド手操作ではない。
- `build_logs/startup_first_20260912/mixed/`: 40秒、同じ遅延・損失。ホストは未作成キャッシュから旧方式、クライアントは新方式。1316確定F一致、差分・欠落0。旧側は263件保存、新側は296枚直接転送・キャッシュ保存0を確認。
- Computer Useでキャラクター選択、ステージ選択、ラウンド遷移とTIME UPを確認。`character_select.png` / `stage_select.png` / `battle.png` / `battle_2.png` を今回のログ直下に保存した。全演出の画素比較を代替するものではない。
- `audit_final.json`: 正式12試行のDLLハッシュ一致、各試行の独立した空キャッシュ指定を確認。旧側はコピーごとに263ファイル作成、新側はキャッシュディレクトリ自体を作成しない。今回対象の `MBAACC_1` / `MBAACC_2` の28 INIとゲームEXEは不変。隣接する別プロジェクトの検証コピーは対象に含めない。
- 両テストコピーのCLI EXE/DLLは `build/bin` と同一。EXE/GUI/DLLのPE Machineはすべて0x014c。最終DLLのSHA256は `47b6b5f8e349d833d34b99a960289f18ae0fecfd00b720863bb5a091918aef73`。既存ゲームを停止せず、検証で生成したゲームのみ終了した。

## 再現

```powershell
$env:PATH='C:/msys64/mingw32/bin;C:/msys64/usr/bin;'+$env:PATH
cmake --build build -j8
python -X utf8 src/harness/bench_startup.py --root _TEST_MBAACC --mode training --variant fast --comparison first --empty-cache --label first_fast --out build_logs/first_fast_new
```

`--variant baseline` で従来の初回、`--mode versus` で2窓対戦。出力先は毎回新規にし、テストコピーが起動中なら測定器は停止せず拒否する。実ゲームデータ・ユーザーINIは含めず、ビルド成果物だけをテスト用cccasterフォルダーへ反映する。
