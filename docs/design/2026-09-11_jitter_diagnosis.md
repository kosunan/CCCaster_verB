# 17,000µs前後の1F揺らぎ：実測による切り分け

追記: 本文は修正前の調査記録。後続の実装・校正結果は[実戦キャリブレーション](2026-09-11_jitter_calibration.md)を参照。

## 結論

CPUが1Fの計算に17ms使っているという根拠はない。同期補正による予定締切の変更、相手入力待ち、更新開始後の処理時間差が、それぞれ長い間隔を発生させている。WASAPI由来の出力時計と実QPCの相関にも約100µs単位の変動がある。平均60FPSでこれらを合格扱いにできない。

今回は原因調査用の記録を追加した。待機・補正・描画の動作自体は変更していない。発生要因の特定と、揺らぎの修正完了は別である。

## 測定方法

`CCCASTER_PACE_TRACE=1`のときだけ次の診断を追加する。通常起動では詳細記録を行わない。

- Pace: 通常ゲーム更新前、待機前の音声時計、予定締切、待機後の音声時計と実QPCを採取。音声取得前後のQPCの中点を対応点とし、取得経過も記録する。
- PhasePace: クライアントの位相補正ごとの対象番号・誤差・補正量。
- DisplayPace: PresentフックでHUDの1Fと同じ計測値・WORKを記録。これはモニターの実走査時刻ではない。
- `src/harness/analyze_pace.py <log-directory>`で全対戦区間と終盤480サンプルを別々に集計。試験脚本の第一対戦世代（131072以降）を対象とする。後続対戦まで一般化した集計器ではない。

同一PC2窓、40秒、自動入力、D2/R4、TimeScale1。比較器のREC/FRAME/STATE/MEMは両試験で確認済み1175F差分・欠落0（絶対WTとメニューカウンターを除外）。WASAPIは両側activeでQPC切替なし。診断は時刻取得・ログ追加の費用を持つため完全に無侵襲ではない。

元フォルダーのbuild DLLと両テストゲームDLLのSHA256は調査開始版で一致していた。少なくともこの3ファイルの旧版混在は見つからなかった。ユーザーが見た全場面の再現ではない。

## 1. 補正が17msの締切を作っている

遅延15〜25ms・損失5%を注入した `I:/work_space/CCCaster_v10_experiments/build_logs/bounded_real_20260911_032038/game_2.log`、フレーム131895:

| 内容 | µs |
|---|---:|
| 予定締切間隔 | 17033 |
| 待機後の実QPC間隔 | 17023 |
| 待機後の締切超過 | 5 |
| 直前フレームのWORK | 435 |

実間隔 = 予定間隔 + 締切超過の差分 − (音声時計−QPC)の差分。ここでは17033−4−6=17023。

PhaseFollowerは1観測ごとに最大250µsの小補正をcadence.Shiftへ反映する。1入力番号の採取前に複数の新観測を処理できるため、1観測の上限と1F合計の上限は同じではない。ハンチング抑制は補正方向の振動を抑えるが、瞬間周期の変動量までは小さくしていなかった。前回の実装上の不足である。

## 2. 大きな乱れは入力待ちにも対応する

同試験ホストのフレーム131346は実間隔45711µs、待機前から締切を29000µs超過。既存ログに `WAIT reason=remote input ... elapsedUs=29769` がある。直前WORKは398µs。CPU計算45msの証拠ではなく、入力未着を待つ既存の上限付き同期方式による停滞が対応する。

全対戦の17,000µs以上はホスト154/940、クライアント145/939。終盤480件に限ると0/480と1/480。終盤だけを使って全試験良好とは判定しない。

## 3. 表示間隔は処理時間の前後差でも揺れる

遅延・損失注入なしの `build_logs/bounded_real_20260911_032227` では通常更新前の実間隔は両側938件中17,000µs以上0件。全範囲はホスト16453〜16834µs、クライアント16410〜16834µs。

ただしHUDと同じ表示間隔は、終盤480件中両側2件ずつ17,000µs以上。ホストのフレーム131895→131896でWORKが589→1783µsへ増え、後者の表示間隔は17860µs。クライアントも511→1569µsで17715µsとなった。

現行は更新開始を締切へ合わせ、その後のゲーム更新・描画準備完了時にPresentへ到達する。したがって表示間隔には前後のWORK差が加わる。WORKは純粋なCPU実行時間ではなく、この境界間の経過時間であり、OS中断やドライバー待ち等を含み得る。1.8msになったWORKの内部関数別内訳は今回未特定。

この無劣化試験では位相補正ログは0件、ロールバックも0回。比較器のpassed=falseはロールバック発生要求を満たさないためであり、状態不一致によるものではない。

## 4. 時計相関の小さな変動

無劣化試験ホスト131090: 予定間隔16667µs、締切超過差分0、音声時計−QPC差分+142µs、実間隔16525µs。時計の出力相関の変動がそのまま待機の長短へ入る例である。

現在はIAudioClockの位置と相関QPCから毎回補間し、ClockContinuityで単調性を保つ。位置相関の細かな変動が残る。デバイスそのもの、ドライバー、補間・連続性処理のどこが主因かまではこの測定だけで断定できない。

待機後の時計取得経過は通常0〜1µs（整数µsで丸めた値）。この計測点ではAPIやmutexの数百µs占有は主因として見つからなかった。待機中の全取得を計測したわけではないので、競合が一切ないとは結論しない。

[MicrosoftのGetPosition仕様](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition)も位置とQPCを対応させた外挿を説明している。WASAPIの採用自体がOSの実行開始や表示時刻を保証するものではない。

## 修正の優先順位（未実施）

1. 小さな位相補正の予算を「観測ごと」から「1入力フレームごと」へ変え、数フレームに分散。大きな追いつきと通常周期を明確に分けて記録する。
2. WASAPI相関の安定したモデルを使い、締切直前の短区間を実QPCで外挿。音声を基準に保ち、原点を不連続に動かさない。
3. 表示時刻まで揃える場合、更新開始とは別にPresent締切を設計する。入力遅延との交換条件があるため単純な待機追加はしない。
4. 入力待ち・ロールバック・純粋な通常更新を引き続き分ける。入力未着を待つ要件と、すべての実更新を絶対に同間隔にする要求は同時に常には成立しない。

15既存テスト成功。同期・待機の修正前後比較ではなく、2条件の原因切り分けである。
