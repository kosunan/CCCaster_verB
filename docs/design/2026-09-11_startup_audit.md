# トレーニング・プレイヤー対戦への起動経路を解析する

後続作業: [10人による実装と短縮実測](2026-09-11_startup_implementation.md)。以下は実装前の初回調査記録。

## 調査範囲と結論

2026-09-11。現行コード、既存ログ、ローカルの対象ゲームを逆アセンブルして調査。今回のプレイヤー対戦はGUIのオンライン対戦（Versus）を指す。

ユーザーの今回の明示指示を旧サブエージェント禁止より優先して3人を起動したが、4人目の作成はツールのagent thread limitで拒否された。10人を使用したとは扱わず、同じ3人への追加依頼で10件の調査を実施した。

**高速化の実装・新規実機試験・短縮秒数の測定は今回行っていない。** 調査資料と未解決事項だけを更新する。既存の未コミット変更、設定、ゲーム、稼働プロセスを保全した。

優先候補は、(1) 到達時間の正しい計測、(2) 正規モード分岐パッチ適用後の方向入力省略、(3) 対戦交渉の固定2秒を条件成立による移行へ置換、(4) DLLの100ms待機とダミーD3D初期化の実測。計算量の大きい探索を直すより、待機・重複初期化・不要な状態遷移を減らす問題である。

## 現行経路

Training: GUI開始 → worker → CreateProcess → エントリ到達待ち → DLL注入 → ゲーム再開。DLLは別スレッドで設定読込み → Sleep(100) → IPC読込み → ゲームパッチ → TimeHooks → NetplayManager → DxHook → SceneRunnerを準備する。その後ゲームスレッドの高速起動がタイトル・メニューを通過し、キャラ選択へ到達する。

Versus: 上記の前に相手との交渉と接続後2秒のauto-lock待ちが入る。DLL側のREADY・時計推定は別処理で、起動処理と並行して進む。キャラ選択では同期・世代バリア・入力待ちを通る。相手を待つ時間と自分のゲームロード時間を分けて測る必要がある。

現行`SceneFastBoot.cpp:129`はTraining=5、Versus=1のナビ回数を設け、Downと解放を交互に送る。しかしForceGoto適用後は項目判定自体を飛ばす。旧`I:/work_space/CCCaster/OLD/targets/DllNetplayManager.cpp:97`も目標モード既知時はConfirm交互のみで、方向入力はない。**パッチ成功を確認した場合だけDownを省く**のが小さい改善候補となる。

現行のパッチ処理は元命令照合、VirtualProtectの成功確認、FlushInstructionCacheが不足している。改善では元命令と分岐先の命令列を照合し、ゲームスレッドで適用、保護・書込み・命令キャッシュ更新成功後に適用済みとする。不一致時は未知の命令を上書きせず、既存入力経路を維持する。

現在modeを20へ直接書く方法は、正規初期化を省くため採用しない。フェードも初期値・副作用・オブジェクト寿命を未確認であり、省略案は保留。0.0625から単純に「16F短縮」と断定しない。ロゴ・資源ロードを安全に省く入口は今回未特定。旧版の派生入力書込みとCC_SKIP_FRAMES_ADDR書込みは移植しない。

## 待機と計算量の評価

| 優先 | 現行コード | 評価・改善条件 |
|---|---|---|
| 高 | `SessionNegotiator.cpp:264` 接続後2秒待ち | GUI対戦でもゲーム生成前に待つ。双方確認と再送・移管を設計して置換する。単純0秒化不可 |
| 高 | `dllmain.cpp:159` Sleep(100) | 固定待機を準備条件で置換する候補。ただしゲーム本体の初期化と重なるため100msの総短縮保証はない |
| 中 | `DxHook.cpp:92` ダミーHALデバイス生成・破棄 | vtable取得のための重複資源準備。実時間を測ってからゲームのCreateDevice捕捉を検討 |
| 中 | `GameFrameOrchestrator.cpp:220` 初回EndScene | フォント2件、ImGui、WndProc、DirectInputを直列準備。入力と描画の準備を分離する候補。キャラ選択へ停止を移すだけにしない |
| 低 | GUI末尾64KiBの再読込み・再解析 | 増分読取りでO(新規ログ量)にできる。現状も上限付きで、総起動時間の主因という証拠なし |
| 表示 | MainController 200ms、GUI起動中100msポーリング | ゲームの前進を止めない。イベント化は主に完了通知の遅延を減らす |
| 異常時 | `GameLauncher.cpp:101` エントリ待ち、注入のINFINITE待ち | 別EIPを正常取得し続けるとtriesが増えず無期限。段階別の実時計期限と失敗理由を追加する候補 |

対戦の2秒は双方合意ではなく応答猶予。Hostは最初の探索パケットでconnected=trueとなり、送信より前にauto-lockを判定する。0秒化すると返答せずsocketを破棄し、Clientを交渉に残し得る。現在の移管はsocketそのものの引渡しではなく、ランチャーが閉じたportをDLLが再bindする方式である。

置換にはpacket形式・版・peer・nonceの検証、Readyの再送、相手の受領確認、片側移管後も遅れた交渉へ応答できる方式が必要。最後のACK消失を扱わず「echoを1回見たら終了」としても十分ではない。単にsocketを二重bindして寿命を延ばす案も受信先を曖昧にする。交渉のping/jitter値はゲームへ渡しておらず、2秒の統計蓄積自体はゲームの時計同期の必須条件ではない。

ゲーム本体にはDirect3DCreate9のIATが存在するが、現行は捕捉していない。ダミーデバイスを除去する場合はDirect3DCreate9→CreateDevice→実デバイスのフック設置が候補。ただし現ランチャーはLoadLibrary完了だけを待ち、別InitThreadのフック設置を待たずゲームを再開する。生成APIを取り逃がさないよう、entry解放前の入口設置完了を保証する必要がある。現方式が持つ「デバイス生成後でも捕捉可能」という性質を失わない対策が必要となる。

ImGui分離時もWndProcだけを先行させない。現行UIManagerはImGui::GetIOを無条件に呼ぶ箇所があり、未作成時のガードと入力・描画それぞれの成功状態管理が必要。ダミーHAL除去は総仕事量の削減、ImGui遅延は仕事の実行時点の移動として評価を分ける。

## 既存計測の限界

- 最新8組・16起動（`build_logs/bounded_real_20260911_074130`〜`075132`のlauncher_1/2.err）では、DLL注入完了は内部計測開始から2〜5ms、entry解放は3〜6ms。**CreateProcessとエントリ到達待ちは計測開始より前**なので総起動時間ではない。
- `build_logs/gui_20260911/training_real.log`の30.5秒は起動維持の確認であり、Training到達時間ではない。
- 高速起動中のframe=30を通常60Hzの0.5秒へ換算できない。
- `SceneRunner.cpp:364`はphase<CharaSelectでのみFastBootを呼ぶが、その内部の完了判定はmode=CharaSelect。通常の到達時には呼出しが遮られ、完了フラグと到達ログが実行されない。通常速度への復帰はSceneRunner側で行われるので、速度復帰失敗とは区別する。
- `dllInitialized=true`はIPC読込み直後で、ゲームパッチ・フック・SceneRunner準備より前。Training Readyを操作可能時刻として扱えない。

## 次の比較実験

1. 同一PC内で共通の実QPCを使い、GUI操作、worker入口、接続成立、CreateProcess前後、entry到達、注入、DLL準備末尾、最初のStep、キャラ選択検出を一回ずつ記録する。別PCのQPC生値同士は引き算しない。
2. 非skipのoriginal_Present直前・直後とHRESULT、キャラ選択で通常入力経路を初めて通った時刻を分ける。onAfterPresentはskip時にも呼ばれるため提示の証拠にしない。成功Presentも物理モニターの発光時刻とは区別する。
3. TrainingとVersusを別集計し、双方のモード・入力・同期成立を確認。起動直後と反復起動を区別し、同条件で変更前後を交互に比較する。初回起動だけでOSキャッシュが空の「完全コールド」とは断定しない。
4. まず命令照合付きDown省略を単独比較。次にSleep(100)とD3D準備の実費用を測る。対戦の2秒置換は別変更として、損失・片側遅延・移管直前のpacket消失を確認する。
5. 単純な成功最短値だけでなく到達時間の分布・失敗数を保存する。フック・入力・通信の実装を変える際はcccaster-verifyの32bitビルドと必要な短い実ゲーム試験を行う。既存3秒/30秒の待機契約、F4遮断、世代/RNG/再送を維持する。

ウォーム条件は変更前後各3回以上を初期比較とし、全試行値と中央値を示す。少数試行からp99や一般的な保証は出さない。合格には目標モード、初回実Present成功、通常入力到達を要求し、最終候補ではTrainingの戦闘到達・対戦の確定入力/状態一致まで確認する。測定のばらつきと区別できない差は効果未確認とする。
