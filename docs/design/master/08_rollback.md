# 08. ロールバック — 状態保存と再計算

## 責務

この章の対象は「**予測して先に進み、外れたら巻き戻して計算し直す**」機構である。

具体的な担当範囲:

- ゲーム状態のスナップショット（何を、いつ、どこへ保存するか）
- 相手入力が無いフレームの予測と、予測失敗の検出
- 巻き戻し（LoadState）と再計算（Rollup）のフレーム内タイミング
- 巻き戻してはいけないもの（SFX / リプレイ / 通信状態 / 描画）の隔離
- ロールアップ性能の計測と表示（roadmap 4-5 の「重要デバッグ要件」）

**担当しないもの**: フレーム番号の意味（04章）、入力の取得と配信（05章）、
パケット形式（06章）、いつロールバックを有効化するかの判断（07章）。

**この章だけは「まだ存在しないものの設計」である。** `rollback/` 一式は
`src/core_dll/CMakeLists.txt` でビルド対象から除外されており、現在のバイナリには
1バイトも入っていない。呼び出し元も存在しない。以下の「現状の構造」は
**動いているコードの記述ではなく、棚に置かれた部品の在庫表**である。

## 成立の前提条件

ロールバックは、下記が**すべて**成立して初めて意味を持つ。1つでも欠けると、
実装は完成しても静かに間違った答えを出し続ける（現在のデシンクと同じ質感になる）。

| # | 前提 | 現状 | 担当章 |
|---|---|---|---|
| **前提1** | **フレーム番号がゲーム進行と一致している** | ❌ 未成立。`netFrame` は「背圧を通過した Present の回数 + 200」で、WT と突き合わされていない | **04章** |
| **前提2** | 決定性: 同じ状態 + 同じ入力 → 同じ結果 | ⚠️ 未検証。MBAA 側は満たすと推定するが、FPU 環境・保存漏れで壊しうる（下記） | 08章 |
| **前提3** | 保存すべき状態が漏れなく列挙されている | ⚠️ `DumpEntryList` はあるが検証手段が無い | 08章 |
| **前提4** | ロールバックを有効/無効にする権威が1つある | ❌ 未成立。IntroBarrier は戻り値が捨てられ、何もブロックしていない | **07章** |
| **前提5** | ゲームメモリを DLL から任意時点で読み書きできる | ✅ 成立（`Present` フック内は安全） | 02/03章 |

### 前提1 — 第4章が未完なら、ロールバックは原理的に成立しない

ロールバックの全操作は「フレーム番号」を引数に取る。`Load(f)` / `rerun f..current` /
`ConfirmRemote(f, input)` のすべてがそうである。番号がゲームの瞬間を指していなければ、
**正しく実装されたロールバックが、正しく間違った状態を復元する**。

現状の番号は 04章 P-2 のとおり `starve` の回数だけゲームからずれる（実測で恒等式が確認済み）。
この状態でロールバックを繋ぐと、自分の `F=1000` と相手の `F=1000` が別のゲーム瞬間を指すため
予測外れが常時発生し、巻き戻し先も相手の想定と別の瞬間になるので再計算しても収束しない。
そして予測外れが常時発生する以上、**毎フレーム最大深度のロールアップが走り性能も破綻する**。
つまり「番号がずれている」不具合が、ロールバックを入れると「重くて直らない」不具合に化ける。
**04章の S2（採番の WT 切替）完了が、この章の着手条件である。**

### 前提2 — 決定性と FPU 環境

MBAA は 32bit x86 の単一スレッドゲームであり、同じ状態から同じ入力で回せば同じ結果になる
**はず**である（推測: 逆アセンブルによる確認は行っていない）。ただし DLL 側で壊しうる経路が2つある。

1. **FPU 環境**。MBAA は x87 と SSE を使う（`CC_P1_GUARD_BAR_ADDR` 等が float）。
   x87 制御語（丸めモード・精度制御）と MXCSR は**グローバルな状態**で、DLL が呼ぶ他ライブラリ
   （ImGui / D3D9 / asio / CRT）が変更しうる。丸めモードが違えば同じ入力から違う結果が出る。
   `StateRingBuffer` が `fegetenv/fesetenv` でこれを保存・復元しているのは**正しい判断**である。
   > 推測: MinGW の `fenv_t` は x87 制御語・状態語と MXCSR を含むが x87 レジスタスタックは含まない。
   > フレーム境界（Present）ではスタックは空のはずなので実害は無いと見るが、未検証。

2. **時間依存**。`SetTimeMultiplier(1000)` により、ゲームが実時間 API を読むと 1000 倍速の値が返る。
   ゲームロジックがそれを参照して分岐すると、再計算で別の値を読み、同じ入力から別の結果が出る。
   > 推測: MBAA の対戦ロジックは WorldTimer（自前カウンタ）駆動で、実時間 API はフレームリミッタ
   > にしか使っていないと考えられる。実測 B-2（`Present : WT = 1:1` が 98サンプル×2機で例外なし）は
   > この推測と整合するが、直接の証拠ではない。

### 前提3 — 保存の完全性

保存漏れは「たまにしかずれない」形で現れるため、最も発見が遅れる。
漏れた変数は、巻き戻し後に**未来の値のまま**残り、再計算の入力を汚染する。

保存すべきものの分類（漏らすと何が起きるか）:

| 分類 | 具体例 | 漏らすと |
|---|---|---|
| RNG | `CC_RNG_STATE0..3`（228B） | 同じ攻撃が別のヒット効果になる。最も再現しにくいデシンク |
| キャラのシーケンス | `CC_P*_SEQUENCE` / `SEQ_STATE`（構造体内） | 技のフレームが1つずれ、以降すべてずれる |
| タイマー | `WorldTimer` / `RoundTimer` / `RealTimer` | 時間切れ判定・演出遷移がずれる |
| 位置・速度 | 構造体内（`X_POSITION` 〜 `Y_ACCELERATION`） | 位置がじわじわ乖離する |
| 勝敗・ラウンド | `WINS` / `ROUND_COUNT` / `GAME_POINT_FLAG` | ラウンド終了判定が食い違う |
| カメラ | `CC_CAMERA_X/Y` | 見た目のみ。ただし当たり判定に使うなら致命 |
| SFX | `CC_SFX_ARRAY`（1500B） | **保存してはいけない**（後述） |

#### `MemDumper` の効き方（実算）

`DumpEntryList` の 24 エントリを 64B ギャップ吸収で統合すると 12 ブロックになる。

```
0x555130  11248 B  プレイヤー構造体 ×4 (0xAFC×4)。全体の 96%
0x564068    228 B  RNG_STATE2 + STATE3（4B ギャップ吸収）
0x559548    116 B  game point / wins（散在 4 エントリを1本に）
0x55D1D4     56 B  WorldTimer + pause + intro
0x562A3C     44 B  round/real timer + training pause（32B 吸収）
0x564B14     32 B  camera X/Y + versus pause（20B 吸収）
他 6 ブロック 28 B
合計         11,752 B / state
```

**判断: 状態サイズは 11.7 KB で、`memcpy` の実行時間は問題にならない。**
15 スロットでも 176 KB で L2 に収まる。**性能上の律速は再計算のティックであり、
保存・復元ではない。** ここに最適化の労力を割く必要はない。

## 目指す設計

### 設計原則

1. **番号の権威は 04章にある。この章は番号を作らない。**
   `netFrame` を受け取り、そのまま使う。独自のフレームカウンタ（現行 `_currentFrame`）は持たない。
   持つと 04章の番号と二重管理になり、ずれた瞬間に発見できない。

2. **ゲームメモリを書き換える操作は、すべてゲームスレッドで行う。**
   通信スレッドは `MatchInputBuffer::ConfirmRemote` で「食い違った」という**事実だけ**を記録し、
   `ConsumeMismatch()` をゲームスレッドが `Present` の中で拾う。R-2 の構造は採らない。

3. **再計算は「協調型」で行う。ゲームを for ループで回さない。**
   DLL からゲームの1ティックを呼ぶ口が無いので、再計算の1フレームは `Present` の1周に対応する。
   ロールアップ中は `onPresentSkip` で実際の描画を飛ばし、Metronome の待機も飛ばす。
   結果として**画面上は1フレームのまま、内部で N ティックが進む**。
   （既存 `ProcessRerunFrame` の「for ループなし。ゲーム本体に制御を返す」という判断は正しい。
   これは 02章のフック構成から強制される唯一の形である。）

4. **巻き戻せないものは、そもそも巻き戻しの対象に入れない。**
   音・リプレイ記録・通信状態・描画・オーバーレイは、状態スナップショットの外に置き、
   個別の補正規則を与える。

5. **性能は「測ってから」チューニングする。**
   状態サイズ 11.7 KB は既に十分小さい。律速は未測定のゲームティックである。
   計測を先に入れ、`memcpy` の最適化には手を出さない。

### 状態の定義（何を保存するか）

#### スナップショットの意味を1つに固定する

`Present` はゲームの1ティックが**終わった後**に呼ばれる。したがって:

```
S[f]  ≡  Present コールバック f の時点でのゲーム状態
      =  フレーム f のティックが完了した直後
      =  フレーム f+1 のティックを実行する直前

I[f+1] ≡ Present コールバック f で WriteInput したもの
      =  フレーム f+1 のティックが消費する入力

不変条件:   S[f] + I[f+1]  →  S[f+1]
巻き戻し:   フレーム m の入力が間違っていた  ⇒  Load(S[m-1]) して m から再実行
```

**この定義を文書とコードの両方に明記する。** 既存 `RollbackEngine` は
`Load(mismatchFrame)` してから `mismatchFrame` から rerun しており、
「`S[f]` = f を実行する直前」という別の規約を採っている。**どちらでもよいが、
混在すると 1 フレームずれ、症状は「たまにデシンク」になり原因特定が極めて困難になる。**

#### 保存対象

`DumpEntryList` の 24 エントリ（→ 12 ブロック / 11,752 B）＋ `fenv_t` を1単位とする。
**RNG・シーケンス・タイマー・位置は既に含まれている**（前提3 の表と `DumpEntryList` の対応を確認済み）。

保存**しない**もの:

| 対象 | 理由 |
|---|---|
| `CC_SFX_ARRAY`（1500B） | 音は既に鳴っている。巻き戻して鳴らし直すと二重再生になる。別機構（SFX フィルタ）で扱う |
| リプレイ構造体 | 巻き戻しではなく**ポインタの巻き戻し**で扱う（後述） |
| `MatchInputBuffer` / 通信状態 | ロールバックの対象外。巻き戻すと相手入力の確定が消える |
| ImGui / オーバーレイ / DirectInput | ゲーム状態ではない |
| `CC_FPS_COUNTER` / `CC_ALIVE_FLAG` | 計測・生存確認であり、ゲームロジックの入力ではない |

#### リングの寸法

| 項目 | 値 | 根拠 |
|---|---|---|
| スロット数 | `MAX_ROLLBACK + 2` | R-7 の余裕ゼロ問題を解消。深度 15 なら 17 |
| 1スロット | 11,752 B + `fenv_t` | 実算 |
| 合計 | 約 200 KB | L2 に収まる。ヒープ確保はセッション開始時の1回のみ |
| SFX 履歴 | `MAX_ROLLBACK + 2` × 1500 B ≒ 25 KB | R-8 の 384 KB を解消。周期を状態リングと揃える |

### フレーム内のタイミング

```
(A) Phase 検出
(B) フェーズ遷移
(C) FastBoot

          ring.Load(m-1) + fesetenv        ← 状態と FPU 環境を戻す
          FixReplayPointers(depth)
          InitSfxFilter(m, current)
          rollupPending = true; rerunFrame = m
      }

★ (R2) ロールアップ 1 ステップ — rollupPending の間だけ
      入力 = (local[rerunFrame], resolved remote[rerunFrame])
      GC::WriteInput(...)                  ← (F2) の代わりにこちらが書く

      SaveRerunSounds(rerunFrame)
      ++rerunFrame
      if (rerunFrame > current) { rollupPending = false; FinishedRerunSounds(); 計測確定 }
      → onPresentSkip = true を要求して return（この Present は描画しない）

(F)  MatchScene ディスパッチ        ← ロールアップ中はスキップ
(F2) 通常の入力配信                  ← ロールアップ中はスキップ（(R2) が書いたため）
(R3) スナップショット取得 — 通常フレームの末尾
      相手入力が未確定のフレームだけ Save（確定フレームは巻き戻し起点にならない）
(G)  ログ・疎通チェック
```

#### 1フレームの予算

| 項目 | 見積 | 根拠 |
|---|---|---|
| 1フレームの総予算 | 16,666 μs | 60fps |
| ゲームのティック + 描画 | **未測定** | 最初に測るべき値 |
| スナップショット保存 | 約 1〜3 μs | 11,752 B の `memcpy`。推測: 一般的な帯域から |
| 状態復元 | 約 1〜3 μs | 同上 |
| **ロールアップ全体の許容上限** | **5,000 μs（暫定）** | 予算の 30%。超えると Metronome の catch-up 債務になり、04章 P-4 のフリーランを誘発する |
| 深度 15 のときの 1 ティック当たり許容 | **333 μs** | 5,000 ÷ 15 |

**判断: 「1ティックが 333 μs 以内か」がロールバック実現可否の分水嶺である。**
ロールアップ中は描画（`Present` 本体）と Metronome 待機を飛ばせるので通常フレームより
速いはずだが、確証は無く実測でしか分からない。**S1 で最初に測る。**
（推測: MBAA は 2008 年のゲームであり、描画を除いたロジックティックは数十 μs の
オーダーと見るが、根拠は無い。）

### 予測と巻き戻し

#### 予測方式

| 案 | 内容 | 採否 |
|---|---|---|
| **A. 直前フレームの繰り返し（採用）** | `predict(f) = resolved(f-1)` | ✅ 格ゲーの入力は連続性が高く、ヒット率が最も高い。GGPO を含め業界標準 |
| B. 最後の**確定**入力の繰り返し | `predict(f) = remote[lastConfirmed]` | ❌ 現行 `SceneRunner.cpp:171-174` がこれ。確定が遅れると古い入力を延々と繰り返し、外れ率が上がる |
| C. ニュートラル固定 | `predict(f) = 0` | ❌ 押しっぱなしを全部外す |

**現行コードは B なので、A に変更する。** これは 05章と共同の変更である。

#### 予測外れの検出

器は既にある（`MatchInputBuffer.hpp:73-98`）。`ConfirmRemote` が
「そのフレームの `predictedRemote` と実際の入力が違う」ときに `RecordMismatch(frame)` する。
**最も古い不一致が優先される**（`:247-250`）ため、巻き戻し起点として正しい。

現状の穴:

| 穴 | 内容 | 対処 |
|---|---|---|
| 消費者が居ない | `ConsumeMismatch()` の呼び出し元がゼロ | (R1) を追加 |
| ローカル未書込み時に検出しない | `ConfirmRemote` は `localFrame == frame` のときだけ予測と比較する（`:86-89`）。相手入力が先に届くと比較されない | 相手が先なら予測自体が不要なので**正しい**。ただし「予測前に確定した」ことを記録しておくと予測ヒット率の分母が正確になる |
| 偽の不一致 | 冗長入力が未書込みフレームを 0 として確定（AUDIT B-5）→ 偽の予測外れ → 無駄なロールアップ | **06章で有効ビットマスクを入れるまで、ロールバックは有効化できない** |
| `ConsumeMismatch` の競合 | `exchange(false)` と `_mismatchFrame` の読みが分離しており、その間の記録を取りこぼす | 単一の 64bit atomic（フラグ + フレーム）に畳む |

#### 巻き戻し量

| 状況 | 深度 | 扱い |
|---|---|---|
| 通常の予測外れ | `current - m`（1〜R） | ロールアップ |
| `m` が epoch をまたぐ | — | **巻き戻さない**。前ラウンドのパケットの遅着として破棄し、計上する |
| `depth > MAX_ROLLBACK` | — | 復旧不能。スナップショットが既に無い。デシンクとして 07章に報告 |
| `S[m-1]` が無い | — | 同上。**確定済みだったフレームの再確定で値が変わった場合**（`ConfirmConflicts`）にここへ来る。これは通信破綻かデシクの証拠であり、黙って続行してはならない |

#### `readPos` の意味が変わる（05章と共同、重要）

現在の入力配信は `readPos = writeHead - (D + R)` で、**R フレーム分を「待つ」ことで
ロールバックを回避している**。ロールバックを入れる目的は、この R を待たなくすることである。

| | 現在（ロールバック無し） | ロールバック導入後 |
|---|---|---|
| `readPos` | `writeHead - (D + R)` | `writeHead - D` |
| 相手入力が無いとき | 書かない（保持） | **予測して進む** |
| 体感遅延 | D + R フレーム | D フレーム |
| 背圧 | `lead > D + R` で番号を止める | 04章 C-2 により Metronome を伸ばす |

**この切替は不可逆的に危険である**（予測して進んだ後は、巻き戻せなければデシンク確定）。
移行手順で「ロールアップは走るが `readPos` は据え置き」の段階を必ず挟む。

### 巻き戻してはいけないもの

| 対象 | 問題 | 扱い |
|---|---|---|
| **SFX** | 再計算で同じ音が再度トリガされると二重再生になる。逆に、巻き戻しで「鳴らなかったことにする」ことは物理的に不可能 | **SFX フィルタ**: 巻き戻し区間で既に鳴った音を `_sfxFilterArray` に OR で集約し、再計算中の再トリガを抑止する。再計算後に「巻き戻し前は鳴ったが再計算では鳴らなかった」音は、**ミュート音量で再生してキャンセルする**（`DX_MUTED_VOLUME = 0xFFFFD8F0`）。既存 `InitSfxFilter/SaveRerunSounds/FinishedRerunSounds` がこの構造だが、**R-4 のとおりミュート側が未接続で、現状は逆効果になる** |
| **リプレイ記録** | ゲームはフレームごとにリプレイ入力を記録し続ける。再計算するとその分が二重に記録され、リプレイが伸びて壊れる | `FixReplayPointers(depth)`: 巻き戻した分だけ記録ポインタを戻す。`RepInputState.frameCount` が 1 なら要素ごと削除、それ以外なら減算（既存実装の方針は妥当）。**要検証: リプレイ自動保存が OFF のときポインタが NULL かどうか**（現実装は NULL で `break` するので安全側） |
| **描画 / Present** | 再計算の中間フレームが表示されると早送りに見える | ロールアップ中は `onPresentSkip` を true にして元 `Present` を呼ばない（02章の既存機構をそのまま使う） |
| **通信状態** | `writeHead` / 送信済みフレーム / ソケットは巻き戻し対象外 | スナップショットに含めない（含めていない） |
| **オーバーレイ / DirectInput** | ゲーム状態ではない | 同上。ただしロールアップ中は ImGui のフレームを開始しないこと（`RenderSkip` の既存経路） |
| **Metronome の位相** | 巻き戻すと時間が戻ることになる | 対象外。ただし**ロールアップに要した実時間は catch-up 債務になる**ので、04章 C-6 の catch-up 上限が先に入っていること |

### 性能要件と計測

roadmap 4-5 が「Rollup にかかる性能・処理時間を画面へ表示せよ」と要求している。
**何を測るかを先に決める。**

| 指標 | 定義 | なぜ必要か | 表示 |
|---|---|---|---|
| `rollupUs` (last / mean / p99) | (R1) 開始から (R2) 完了までの**実時間** | roadmap の直接の要求。p99 が予算を超えたらチューニング対象 | ✅ 常時 |
| `rollbackDepth` (last / max / ヒストグラム) | `current - m` | 深度が張り付いていれば予測が機能していない | ✅ 常時 |
| `rollbacksPerSec` | 1秒あたりのロールバック回数 | 60/s に近ければ毎フレーム巻き戻している＝設計破綻 | ✅ 常時 |
| `predictHitRate` | 予測が当たった割合 | 予測方式（A/B/C）の評価。回線品質の指標にもなる | ✅ 常時 |
| `saveUs` / `loadUs` | `MemDumper::SaveState/LoadState` の実時間 | 律速がティックか memcpy かを切り分ける | デバッグ時 |
| `tickUs` | ロールアップ中の 1 Present あたり実時間 | **予算判定の本体**。333 μs を超えるか | デバッグ時 |
| `desyncEvents` | 深度超過 / `ConfirmConflicts` / epoch またぎ破棄 | 0 でなければロールバックは信用できない | ✅ 常時 |

**計測は必ず `TimeHooks::RealQueryPerformanceCounter()` を使う。**
`SetTimeMultiplier(1000)` により通常の QPC は 1000 倍速の値を返すため、
素の `QueryPerformanceCounter` で測ると 1000 分の 1 の値が出る。
（既存 `RollbackEngine.cpp:11-17` はこれを正しく行っている。**この判断は保存する。**）

計測値は 09章のオーバーレイに出すが、**同時に harness のログにも出す**こと。
実機の目視だけでは回帰を検出できない。

### 移行手順

各段階は単独でビルド・検証でき、途中で止めても回帰しないように区切る。
**S0 の着手には 04章 S2 と 07章の有効区間定義が完了していることが条件。**

| 段階 | 内容 | 前提 | 検証できること |
|---|---|---|---|
| **S-1 依存の解消** | 04章 S2（`netFrame` の WT 化）、06章の冗長入力の有効マスク、07章の有効区間 | — | 本章の着手条件がすべて揃うこと |
| **S0 掃除** | `StateBuffer.*` 削除。`std::cout` → `DebugLog`。名前空間を `cccaster::core::rollback` へ統一。`MemDumper` / `StateRingBuffer` / `DumpEntryList` だけを CMake に復帰させる（`RollbackEngine` はまだ入れない） | S-1 | ビルドが通る。既存機能に影響が無い |
| **S1 観測のみ** | 毎フレーム `Save` するだけの経路を InGame 中に有効化。**復元も再計算もしない**。`saveUs` を計測 | S0 | 実際の状態サイズ・保存コスト。`Present` を1回余分に回したときの `tickUs`（描画スキップ時の実測） |
| **S2 決定性の証明** | 「N フレーム前の状態を保存 → そのまま復元 → 同じ入力で N フレーム再実行 → 結果が一致するか」を**単独プロセスで**検証する自己テストモード | S1 | **前提2・前提3 がまとめて検証できる。本設計の可否を分ける判定。** 不一致なら保存漏れ（前提3）か非決定性（前提2）。差分の出たアドレスを二分探索で特定できる |
| **S3 ロールアップの結線** | `RollbackEngine` を 32bit `GameInput` の上に書き直し、(R1)(R2) を `SceneRunner` に入れる。**`readPos` は `writeHead - (D+R)` のまま据え置く** | S2 | ロールアップが走っても結果が変わらないこと（この段階では予測は常に当たる／巻き戻す必要が無いので、走っても無害であるべき）。`rollupUs` の実測 |
| **S4 予測の有効化** | 予測方式を A に変更。`readPos` を `writeHead - D` へ。SFX フィルタとリプレイ補正を接続 | S3 | harness の2プロセスで、遅延・ロスを注入しても入力列と状態が一致すること。`desyncEvents == 0` |
| **S5 計測とUI** | 上表の指標をオーバーレイと harness ログへ | S4 | roadmap 4-5 の要求充足 |
| **S6 実機ゲート** | 等倍2窓 + 実回線。`predictHitRate` / `rollupUs` p99 の実測 | S5 | 実機での成立 |

#### S2 を harness で回すために必要な改造

`DumpEntryList` は絶対アドレス直値であり、MBAA が無いと動かない。
**`IGameMemory` の doc が明示的に seam の対象外と宣言している**ため、現状のままでは 10章に乗らない。

**採用案: ベースアドレス相対化。** `DumpEntry.addr` を `base + offset` とし、実機では `base = 0`、
harness では `FakeGame` が確保したダミー領域を `base` にする。`MemDumper` は無改造で、
`DumpEntryList` の各行を `offset` に書き換えるだけで済む。
`IGameMemory` に Save/Load を足す案は採らない（seam は「意味のある値の読み書き」の窓口であり、
生ダンプは別概念）。実機のみで検証する案も採らない（S2 は保存漏れの二分探索が要り、
実機で1回転数分かかる作業は回らない）。

## 未確定事項

1. **ロールアップ中の 1 ティックの実時間。** 予算の分水嶺（333 μs / 深度15）を満たすか。S1 で測る。
   満たさない場合、`MAX_ROLLBACK` を下げるか、ロールアップを複数の表示フレームに分割する
   （＝一時的に相手より遅れる）ことになる。
2. **`DumpEntryList` の完全性。** S2 の自己テストで検証するまで 24 エントリで十分という根拠は無い。
   特に `CC_P1_COMBO_HIT_BASE_ADDR` の指す先とエフェクト配列。
3. **MBAA が実時間 API に依存していないか（前提2）。** S2 で間接的に判定できるが、不一致が出たとき
   原因を「保存漏れ」と切り分けるには逆アセンブルが要る。
4. **`fenv_t` が MinGW/i686 で MXCSR を含むか。** 含まなければ SSE の丸めモードが復元されない。
   `fesetenv` 前後で `stmxcsr` を読んで確認できる。
5. **`RepRound` 構造体の実際のレイアウト。** `unk1[0x120]` 等がマジックナンバーのままで出典も
   未検証。リプレイ保存が有効な状態で巻き戻すと、この構造体を誤って壊しクラッシュしうる。
   **暫定対処: `CC_AUTO_REPLAY_SAVE_ADDR` を 0 に固定し、リプレイ補正ごと無効化して先に進む**
   という選択肢がある（機能を捨てる代わりにリスクを消す）。
6. **SFX ミュート配列のアドレス。** R-4 の「AsmHacks 経由（後で接続）」が指す先が現ツリーに無い。
   `DX_MUTED_VOLUME` 定数はあるが書込み先が不明。解決しないと、ロールバック中の音は
   「二重に鳴る」か「鳴らない」のどちらかで妥協することになる。
7. **ポーズとの相互作用。** `CC_VERSUS_PAUSE` / `CC_TRAINING_PAUSE` はスナップショットに含まれる。
   07章の有効区間でポーズを除外するのが素直だが、**ポーズ解除の瞬間の扱い**が残る。
8. **`MAX_ROLLBACK` の適正値。** 現在 15（`MbaaAddresses.hpp:31`）。深度上限であると同時に
   体感遅延（D）と回線品質のトレードオフを決める値であり、実測が出るまで根拠は無い。
