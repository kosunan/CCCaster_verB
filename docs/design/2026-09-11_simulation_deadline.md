# WASAPI維持と実ゲーム更新締切（2026-09-11）

## 変更

前の1F表示は表示要求の間隔だった。今回は入力を渡してゲームへ戻る実際の境界を計測し、更新開始そのものをWASAPIの入力採取予定時刻+1000µsに揃える。毎回「今から16ms待つ」方式ではないので、前フレームの処理時間を周期へ累積させない。予定時刻は採取時にフレーム番号と一緒に600枠リングへ保存し、過去枠を後から位相補正で書き換えない。

1000µsは入力公開・スナップショット保存などを締切前に終えるための余裕であり、入力遅延を最大約1ms増やすトレードオフがある。最後の1msは短時間スピンして再起床の誤差を避けるため、その区間のCPU使用量も増える。入力待ち・時計の独立採取・予測上限を維持する。既に締切を過ぎた場合とロールアップは即実行し、フレームも入力も捨てない。

## WASAPIの修正

時計専用の共有音声ストリームに無音データを開始前に投入し、時計取得時に10ms間隔で補充する。GetCurrentPaddingで空き容量を確認し、GetBuffer/ReleaseBuffer(SILENT)を同じ呼出スレッド内で対にして使う。バッファは1秒、無音なのでゲーム音声に音を加えない。時計取得が1秒以上止まる条件での無中断維持は保証しない。

GetPositionが起動直後に返すposition=0を有効時計として使わない。S_FALSE（精度低下）も通常サンプルとして採用しない。微小な補間値の後退で毎回原点を足し直す処理を撤去し、累積的な速度誤差を防ぐ。故障・欠測時の安全なQPC切替は残すが、正常時はWASAPIが実際に動作する。開始と切替はログで区別できる。

前回報告の「WASAPI由来時計が遅かった」という観測は正しいが、欠測・復帰だけが原因という説明は不十分だった。ストリームへの供給不足と起動位置0の採用も修正した。WASAPIそのものの精度の限界と、この実装不備を混同しない。

## 実測表示

- 1F / DISPLAY: 提示要求間隔とそのFPS（従来追加分）。
- STEP / MIN / MAX: ゲームへ入力を渡して戻る境界の実間隔と120サンプルの範囲。再計算を二重計上しない。前進の追いつきによる短い間隔は隠さない。
- WORK: その境界から次のPresent入口までの経過時間。ゲーム更新と描画、OSによる中断を含む。純粋なCPU使用時間ではなく、GPU完了も測定しない。

ゲームの処理量は場面によって変わるため、WORKを常に16666µsにすることは目標にしない。余裕時間を待機へ振り分け、STEPを16666.666…µsに近づける。Windowsの割込みやスケジューリング、相手入力の遅着、処理超過が存在するため、全フレームで誤差ゼロという要求は保証不能。スピンを増やしても保証はできない。実測値を丸めたり、超過を統計から除去したりして達成したように見せない。
