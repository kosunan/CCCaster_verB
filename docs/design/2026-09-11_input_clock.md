# 独立入力時計・進行補正・保存最適化（2026-09-11）

## 入力の流れ

コントローラ → WASAPI基準の入力枠 → 中央バッファ → ゲーム更新。

`InputTimeline`は通信スレッドの約1msポンプから締切を監視する。ゲームのPresentを待って採取番号を進める旧方式から分離した。通常は16666usに端数を加え、60周期で1000000usとする。入力枠nの実測値を、D先のゲーム入力番号へ保存する。ゲームは自分の次の採取が終わるまで待ち、保存済みの自分・相手の入力を順番に適用する。

ゲーム処理・巻き戻し中も採取と送信は継続する。未達の相手入力は前回値で予測し、不一致時は既存の状態復元・再計算へ入る。再計算では新たなゲーム入力番号を発行せず、中央バッファと適用履歴を使う。入力時計に対してゲームが遅れれば、途中の画面転送と通常待機を省いて追いつく。入力番号を飛ばして追いつく処理はしない。

世代境界は採取を停止し、旧入力ACKと新世代・乱数のバリアを通過後に新しい基準を設定する。再戦の選択確定後は採取を止めて既存の高速遷移を使い、他画面を検出した瞬間に高速化を解除する。

OSが採取スレッド自体を長時間止めた場合、失った過去の物理入力は回収できない。過ぎた枠には最後に実測した値を維持し、最新の到来済み枠で物理状態を読む。ゲーム側の処理遅延と採取スレッドの遅延は区別する。Windows上で厳密なリアルタイム動作やゼロジッターを保証するものではない。

## バッファと入力設定

600枠のリングを継続利用し、再送・巻き戻し用の余裕32枠を残して未消費上書きを防ぐ。上限に到達した場合は明示的なエラーで終了する。送信窓は単純な最新10件ではなく、相手の消費ACKに続く入力を含む10件とし、ACKの進行時もすぐに再送する。

DirectInputのポーリング・読み取り・再列挙を同じmutexで直列化する。UIは別の状態履歴をPresentごとに進める。設定用デバイス名は再読込時にキャッシュし、採取側からUIの設定マップを読まない。キーボードはOSの状態を読み、採取スレッドからImGui状態に触れない。F4設定中は生入力を読み続けつつ公開値をニュートラルにし、閉じた後も全解放まで遮断する。

## 相手との進行差補正

旧実装のα補正は呼び出されていたが、α2は時計の絶対時差を周期へ反映する方式で、記録されていた相手の入力フレームは補正に使われていなかった。

通信版7では巻き戻しで後退しない実適用先端を追加した。同一世代の相手進行をRTT/2と受信後経過時間で外挿し、±1F以内は補正せず、それを超える誤差の1/64を周期へ反映する。上限は±500us/周期。異なる世代・250ms超の古い標本・古い順序の進行通知を使わない。外挿は100msまでに制限する。RTTだけでは片道遅延を正確には求められないため推定であり、決定性の保証は入力番号・世代バリア・ロールバックが担う。

α1による両端の恒常的な減速を停止し、D+Rで吸収できない遅延は既存の期限付き入力待機で処理する。時計のθ推定はRTT・開始交渉・診断のために残す。

## 時計

WASAPIの再生位置と、その位置に対応するQPC値から現在時刻を補間する。音声時計が取得できない場合は実QPCへ連続的に切り替え、復帰時も時刻を後退させない。精度はデバイスとドライバーに依存し、WASAPIがすべての機器でQPCより高精度とは断定しない。

API根拠: [Microsoft IAudioClock::GetPosition](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudioclock-getposition)。相関QPC値は100ns単位なのでマイクロ秒へ変換して補間する。

## 保存とロールアップの最適化

保存表3061項目・1241047Bのうち3021項目は4B。Save/Loadをテンプレートで分離し、4Bのコピー・ゼロ埋めを固定長にした。親を先に復元してから子ポインターを解決する順序と、浮動小数点環境・ゲーム内リプレイカーソルの保存を維持する。毎フレームの保存・復元で動的な領域確保はしない。

NULL部分木をまとめて飛ばす案は計測で改善しなかったため採用していない。通常プレイ時の毎回の予測・巻き戻し診断ログも省いた。スクリプト疎通時は詳細記録を残す。

合成32bitメモリへ実保存表を移した比較（GCC -O2、Save+Loadを2000回）:

|条件|変更前|変更後|短縮|
|---|---:|---:|---:|
|全枝が有効|88.041us|79.682us|約9.5%|
|一部NULL|57.286us|53.673us|約6.3%|

保存バイト列は一致。これは合成メモリ上の測定で、実ゲーム全体の高速化率ではない。計測用ソースは `.ai_workspace/bench_snapshot.cpp`、比較元は `.ai_workspace/before_clock_tuning/PointerSnapshot.hpp`。配布物はReleaseビルド。

## 検証

単体11件成功。新規の入力時計確認では、ゲーム停止中の採取、締切前に採取しないこと、採取遅延時の維持、設定画面の遮断、停止、リング上限を確認した。既存のテストへ再送窓と進行補正の条件確認を追加した。

最初の実ゲーム40秒、ネットワーク劣化15/25/5、ログ `build_logs/bounded_real_20260911_002213`。比較可能な確定1700フレームで入力・FRAME・STATE・主要MEMの差分0。ホスト336回、クライアント473回の巻き戻し。深さ最大4。失敗なし。

実コントローラの手操作と、音声デバイスの抜き差しは今回自動確認していない。再戦の長時間試験は前回実施済みで、今回の確認は短い起動・対戦疎通に限定する。

最終Release版も40秒、同じ劣化条件で実ゲーム確認（`build_logs/bounded_real_20260911_002727`）。確定1718フレームで入力・FRAME・STATE・主要MEMの差分0、欠落0、失敗0。ホスト365回・クライアント479回の巻き戻し、最大深さ4。ロールアップ全体の中央値3113/3162us、最大6616/7497us。診断ログと実描画呼出しを含むため、上記のSave+Load合成計測と直接比較しない。異なる実行の中央値からロールアップ全体が高速化したとは結論しない。
