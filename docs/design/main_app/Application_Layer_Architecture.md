# CLI (コマンドラインインターフェース) 設計書

## 1. 概要
本モジュール (`App / CLI`) は、ユーザーが本ツール（CCCaster_v10）を起動した際の**メインエントリーポイント**となる黒いコンソール画面です。
旧版から複雑な設定項目を削ぎ落とし、「対戦ホスト」「対戦ゲスト（接続）」「オフライン起動」の基本フローのみに特化させ、各種設定はゲーム内（Overlay UI）へ移管したシンプルな構造とします。

---

## 2. 画面とメニュー構成

### 2.1 メインメニュー
ツール起動直後に表示される画面です。**キーボードの上下矢印キー（↑ / ↓）** を用いてモードを選択し、**Enter キーで決定**します。また、各メニュー階層では **Escape (ESC) キーを押すことでキャンセルし、一つ前のメニューに戻る** ことができます。選択中の項目は色反転（ハイライト）または `> [ ] <` 記号で強調表示されます。

```text
=======================================
     CCCaster verB 1.0 beta - Rollback Engine
=======================================
(Use UP/DOWN arrows to navigate, ENTER to select)

> [ 1. Netplay ] < (Highlighted)
  2. Training Mode 
  3. Spectate 
  4. Exit 
```

### 2.2 Netplay (1) 選択時の画面遷移
Netplayを選択後、**単一の入力フィールド**でポート番号（HOST）またはハッシュ文字列（CLIENT）を入力します。入力内容により自動でモードが判別されます。

```text
> Enter Port (HOST) or Paste Hash (JOIN)  [Empty = HOST:7500]
> _
```

#### 入力値による自動判別
| 入力値 | 判別結果 | 動作 |
|--------|---------|------|
| 空Enter | HOST (デフォルトポート7500) | ハッシュ生成 → 待ち受け |
| `7500` 等の数値 (0-65535) | HOST (指定ポート) | ハッシュ生成 → 待ち受け |
| ハッシュ文字列 | CLIENT (ハッシュ接続) | デコード → 接続試行 |
| ESCキー | キャンセル | メインメニューに戻る |

#### HOSTモード時のフロー
ポート番号入力（または空Enter）後、自身のグローバルIPを取得し、接続用のハッシュ文字列を生成してクリップボードに自動コピーします。

```text
> Enter Port (HOST) or Paste Hash (JOIN)  [Empty = HOST:7500]
> 7500

Generating Connection Hash...
Listening on Port: 7500
Connection Hash: aBcDeFgH123 (Copied to Clipboard!)
(Press ESC to cancel)

...
Connection established with Guest!
[Opponent] Name: TargetPlayer
[Network] Ping: 12ms | Jitter: 1.5ms | Loss: 0.0%

Launching Game...
```

#### CLIENTモード時のフロー（ハッシュ貼り付け）
ホストから伝えられた接続用ハッシュ文字列を入力（ペースト）して接続を試行します。

```text
> Enter Port (HOST) or Paste Hash (JOIN)  [Empty = HOST:7500]
> aBcDeFgH123

Connecting via Hash...
...
Connected to Host!
[Opponent] Name: HostPlayer
[Network] Ping: 12ms | Jitter: 1.2ms | Loss: 0.0%

Launching Game...
```

### 2.3 Training Mode (2) および Spectate (3) 選択時の画面遷移
- **2. Training Mode**: そのままMBAACCのプロセス（オフラインのトレーニングモード）を即座に立ち上げます。
- **3. Spectate**: 接続先のIPを入力し、対戦中（または待機中）のホストへ観戦者として接続を試みます。

## 3. 処理フローと状態遷移設計

コマンドラインUIは、内部的に**簡易ステートマシン**として動作します。

### 3.1 CLI の AppState 定義
```cpp
enum class AppState {
    MainMenu,
    NetplayConnection,
    Spectating_WaitingForHost,
    GameRunning,
    Exit
};
```

### 3.2 詳細な処理ロジック
- **`MainMenu` / `NetplayMenu` ステート**:
  - `_getch()` や非同期入力APIを利用して**上下矢印キーの入力を監視**。
  - キー入力があるたびにコンソールの現在行を更新し、選択されているメニュー項目のテキストを色反転や括弧記号でハイライト描画するインタラクティブUIとして動作させる。
  - **Enterキー入力時**: 現在選択中の項目の次のステート（画面）へ進む。
  - **ESCキー入力時**: NetplayMenuなどの下層にいる場合はキャンセル扱いとし、上位のメニュー（MainMenu等）へ戻る処理を行う。
- **ホスト接続待機 (`Hosting_WaitingForClient`)**:
  - 外部API等で**自身のグローバルIP（IPv4/IPv6）を自動取得**し、ポートと結合させた上で**クリップボードに自動コピー**する。
  - PING パケットの送受により、**Ping値、Jitter（Pingの揺らぎ・ブレ幅）、パケットロス率**を計測し画面に表示。
- **ホスト側のモード選択 (`Hosting_WaitParams`)**:
  - ゲスト接続後、ホスト側にのみ「Versus (対戦)」か「Training (トレモ)」かを選択させる。
- **名前の表示処理**:
  - 接続完了時、相手から送られてきたプレイヤー名（設定ファイル等の事前読み込み値）を画面に表示する。
- **ゲーム稼働状態 (`GameRunning`)**:
  - MBAACCのプロセス起動（未起動の場合）とフックのアタッチ処理（`GameInterface` モジュールの初期化）を実行。
  - 画面には `[Game is Running... Press Ctrl+C to force quit]` のみを表示し、CLIとしての描画・入力受付は停止（サスペンド）させる。
  - ゲームプロセスが終了、または対戦相手との切断（ネットワークエラー等）を検知した場合、フックを解除（クリーンアップ）し、理由（例: "Connection Lost"）を表示した上で `MainMenu` に戻る。

### 3.3 設定項目とOverlay UIへの移管
- 旧版のCLIにあった「何フレームのディレイで遊ぶか」や「コントローラーアサイン」のメニューは CLIには一切表示しません。（AIが余分なUIの描画・保持を考慮しなくてよくなります）
- CLIの役割は純粋に **「ピア・ツー・ピア(P2P)のコネクションが繋がるまで」** および **「ゲームプロセスを起動し関与するまで」** のルーター・ランチャーとしてのみ機能させます。

# 07 CLI Internal Design (CLI内部デザイン仕様書)

## 1. 概要
メインアプリ (CCCaster_v10.exe) における、CLIからネットワーク接続確立、そしてゲーム起動までの「裏側」のロジック・ステートマシンの設計を定義します。

## 2. アプリケーションステート (`AppState`)
非同期なネットワークイベントやユーザー入力を処理するため、メインループ内で以下のステートを持ちます。

1. **`HandleMainMenu`**: 初期状態。1〜9 の入力を待つ。
2. **`HandleNetplaySubMenu`**: Netplay選択状態。Hash か Direct IP かを選ぶ。
3. **`HandleNetplayHostOrClient`**: Hash方式時、HostかClientを選ぶ。
4. **`HandleDirectIpConnection`**: IP:Port 文字列を入力しパースする。
5. **`HandleNetplayConnection`**: `SessionNegotiator` に制御を移し、UDP Hole Punching および Ping-Pong の成立を(非同期で)待つ。
6. **`HandleSpectateConnect`**: 観戦クライアントとしての接続。
7. **`HandleStubMenu`**: 未実装の項目を選択した際の仮画面。
8. **`HandleLaunchOffline`**: オフライントレモ直行のためのゲーム起動処理。
9. **`GameRunning`**: ゲームプロセスが起動し、DLLがアタッチされた状態。以降CLIの入力受付はサスペンド（停止）される。

## 3. SessionNegotiator の内部挙動
UDP接続確立を担うクラスの動作仕様です。

- **Host待機**: 指定ポートをバインドし、受信を無限ループ（非同期）で待機。
- **Client接続**: IPv4、IPv6のアドレスそれぞれに対して並行してPingパケットを送信。先に応答が帰ってきたIPを採用し、もう片方を破棄する。
- **Auto-Lock機能**: ヘッドレステスト向けに、通信が確立し、安定したパケット往復が2秒間続いたことを検知して「確定（Locked）」状態にするタイマーロジックを実装。

## 4. プロセス起動・IPC (ゲーム連携)
- `IpcManager`: 共有メモリ (Shared Memory) セマフォ等を用いて、確立した接続情報 (IP, Port, Ping値等) をDLLへ書き込む。
- `GameLauncher`: `CreateProcess` で MBAA.exe をサスペンド状態で起動し、フックDLL (`libcccaster_hook.dll`) をリモートスレッドからインジェクト後、レジュームする。

# 08 CLI External Design (CLI外部デザイン仕様書)

## 1. 概要
メインアプリ (CCCaster_v10.exe) における、ユーザーが直接目にするコンソール画面のUIレイアウト、操作方法、各画面の表示内容を定義します。

## 2. 共通レイアウト
すべての画面において、上部にアプリケーションタイトルとバージョン情報を表示します。

```text

     CCCaster verB 1.0 beta - Rollback Engine
=======================================
```

## 3. 画面定義

### 3.1 メインメニュー画面
起動直後の画面。上下キーで項目を選択し、Enterで決定。

## 4. UI操作・描画の仕様
- **ちらつき防止**: `ConsoleRenderer::NativeClearScreen()` を使用してバッファを直接クリアし、`cls`コマンドによる画面のチラつき（フリッカー）を防ぎます。
- **ハイライト**: 選択中の項目は `> [ ] <` で囲み、色反転（背景白・文字黒等）のANSIエスケープシーケンスを用いて強調します。
- **入力キャンセル処理**: テキスト入力中であっても、ESCキーなどの特定シグナルで即座に入力をキャンセルし、前の画面に戻る機能を持ちます。

# CCCaster verB 1.0 beta: CLI 業務画面・UI遷移設計書

本ドキュメントは、再構築されたインデックス駆動型 `MainController` および `ConsoleRenderer` が提供するコンソールユーザーインターフェース（CLI UI）の画面遷移ルール、各画面の業務（ドメイン）定義、および入力仕様をまとめたものです。

---

## 1. 画面遷移マップと業務概要

### 画面階層構造（ツリー図）
どの画面からどの画面へぶら下がっているか、および「何番のインデックス（数字キー + Enter）を押せばどこへ遷移するか」の全体像です。

```text
[A: メインメニュー]
 ├── [0] Netplay
 │    └── [B: プロトコル選択]
 │         ├── [0] IPv4
 │         │    └── [C: ロール選択]
 │         │         ├── [0] Host   ──> [D: 接続設定 (待受ポート入力)] ──> [ゲーム起動処理へ]
 │         │         └── [1] Client ──> [D: 接続設定 (宛先IP:ポート入力)] ──> [ゲーム起動処理へ]
 │         └── [1] IPv6
 │              └── [C: ロール選択]
 │                   ├── [0] Host   ──> [D: 接続設定 (待受ポート入力)] ──> [ゲーム起動処理へ]
 │                   └── [1] Client ──> [D: 接続設定 (宛先IP:ポート入力)] ──> [ゲーム起動処理へ]
 ├── [1] Training Mode
 │    └── [ゲーム起動処理へ (オフライン)]
 ├── [2] Spectate
 │    └── [E: 観戦接続 (宛先IP入力)] ──> [ゲーム起動処理へ]
 └── [3] Exit
      └── [アプリケーション終了]
```
※各画面において `ESC` キーを押すと、基本的には1つ上の階層（親画面）に戻ります。

### 1.1 [画面A] メインメニュー (MAIN MENU)
* **業務内容**: アプリケーションの起動直後にユーザーが最初に目的（対戦、練習、観戦など）を選択するポータル画面。
* **遷移操作**:
    * `0` (または ↑/↓ で合わせて Enter): **Netplay** -> [画面B: プロトコル選択] へ遷移
    * `1` (または ↑/↓ で合わせて Enter): **Training Mode** -> [ゲーム起動処理] へ遷移
    * `2` (または ↑/↓ で合わせて Enter): **Spectate** -> [画面E: 観戦接続] へ遷移
    * `3` (または ↑/↓ で合わせて Enter): **Exit** -> アプリケーション終了

### 1.2 [画面B] プロトコル選択 (SELECT PROTOCOL)
* **業務内容**: ネットワーク対戦を行う際に、下回りとなる通信規格（IPv4 または IPv6）を選択する画面。
* **遷移操作**:
    * `0` (または ↑/↓ で合わせて Enter): **IPv4** -> `_isIpv6 = false` として [画面C: ロール選択] へ遷移
    * `1` (または ↑/↓ で合わせて Enter): **IPv6** -> `_isIpv6 = true` として [画面C: ロール選択] へ遷移
    * `ESC`: キャンセル -> [画面A: メインメニュー] へ戻る

### 1.3 [画面C] ロール選択 (SELECT ROLE)
* **業務内容**: 自らが部屋を立てる（Listen）か、相手の部屋に入る（Connect）かを決定する画面。
* **遷移操作**:
    * `0` (または ↑/↓ で合わせて Enter): **Host** -> `_isHost = true` として [画面D: 接続設定] へ遷移
    * `1` (または ↑/↓ で合わせて Enter): **Client** -> `_isHost = false` として [画面D: 接続設定] へ遷移
    * `ESC`: キャンセル -> [画面B: プロトコル選択] へ戻る

### 1.4 [画面D] 接続設定 (Netplay Connection)
* **業務内容**: 実際に対戦相手とP2P接続を確立するためのネットワークパラメータを入力する画面。役割によって入力プロンプトが変化する。
    * **Hostの場合**: 公開する「待受ポート番号」の入力を求める。
    * **Clientの場合**: 接続先となる「IPアドレス:ポート番号」の入力を求める。
* **入力操作**: 
    * 任意のテキスト文字列を入力し、`Enter` で確定。
    * **確定後**: 入力パースとPing検証（SessionNegotiator）が走り、成功すれば [ゲーム起動処理] へ。失敗すればエラー表示後、再度入力を待機。
    * `ESC`: キャンセル -> 空文字判定となり [画面C: ロール選択] へ戻る。

### 1.5 [画面E] 観戦接続 (Spectate Mode)
* **業務内容**: 進行中の対戦ルーム（ホスト）に観戦者として接続するための画面。
* **入力操作**:
    * 接続先の「IPアドレス」を入力し、`Enter` で確定。
    * **確定後**: (※現在はモックアップ。ダミーのEnter入力を待って [ゲーム起動処理] へ遷移)
    * `ESC`: キャンセル -> [画面A: メインメニュー] へ戻る。

## 2. UI/UX領域における「実務的懸念事項」（10件）

現在のUI設計・実装をプロダクト環境下で運用するにあたり、ユーザー体験（UX）や業務エラー対応の観点から以下の10の不安材料が挙げられます。

### 1. バリデーションエラー時のフィードバック不足
IPアドレスやポートに不正な文字（例: `abc` や `99999`）を打ち込んだ際、「Invalid input」と短く出るだけで、「どこが悪いのか」「どんなフォーマットが正しいのか」の具体的なサジェストが不足しており、ユーザー離脱の要因になり得る。

### 2. 過去の入力履歴（ヒストリー）機能の不在
クライアントとして接続する際、毎回手動で長い「IPアドレス:ポート情報」を打ち込むのは苦痛。過去に成功した接続先IPや、前回Host時に入力したポート番号を記憶し、矢印キーやデフォルト値として即座に呼び出せる仕組みがない。

### 3. 多言語対応（ローカライゼーション）の拡張性欠如
画面のタイトルや「Netplay」「Spectate」といったハードコードされた文字列がコード内に散在（`MenuOption` の定義内など）しており、将来的に日本語や他言語へ切り替える（i18n）仕組みが備わっていない。

### 4. クリップボード自動コピーの通知不備
ホスト時に自身のグローバルIPを取得して自動的にクリップボードへコピーされる機能があるが、画面のログが流れると見逃しやすく、「本当にコピーされたのか」「何を相手に共有すればいいのか」が視覚的に強調されていない。

### 5. 入力文字数の上限・クリッピング防御の不在
「IP:Port」や「接続パスワード」を入力する非同期プロンプト（`GetTextInputWithCancel`）において、文字の最大入力長（maxLength）が制限されていない。100文字以上打ち込まれるとコンソールの折り返し表示が崩れ、Buffer Overflow の温床にもなる。

### 6. 長いPing検証/API待機中の非同期スピナー（ローディング）表示の欠如
「Fetching Global IP Address...」などで3秒最大タイムアウトなどを設定している間、画面がフリーズしたように見えてしまう。進捗を示す `.` のアニメーションやローディングスピナーが無いため、ユーザーが強制終了してしまう恐れがある。

### 7. 文字色コードへの過度な依存（色覚多様性への非配慮）
「成功判定は緑」「エラーは赤」とANSIカラーコードで行っている部分が多いが、コンソールの設定や色覚的特性を持つユーザーによってはステータスが判別しづらい。[!] や [v] といった記号プレフィックスのフォーマットが一部統一されていない。

### 8. アニメーションやサウンドによる「対戦成立」のフィードバック欠如
SessionNegotiatorで接続がロックインされ、ゲームが起動する瞬間（Connection Locked）の演出が静的テキストのみである。とくにホスト側で接続を待っている際、画面から目を離していても相手が入ってきたことが分かるように、`main_app` の実行フォルダと同じ階層にある音声ファイル（例: `beep.wav` 等）を読み込んで再生（`PlaySound` API等の利用）させる仕組みがなく、マッチング成立の強い合図に欠ける。

### 9. IPv6 におけるスコープID入力などの複雑な案内不足
IPv6モードを選択した際、リンクローカルアドレス（`fe80...`）などで接続する場合に `%eth0` のようなインターフェイスID（スコープID）が必要になるケースがあるが、入力画面では単純な `[IPv6]:Port` しか案内されておらず、ネットワーク不慣れなユーザーが躓くポイントとなる。

### 10. AI自動化・ヘッドレス検証（疎通テスト）への非互換性
現在のUIフローは標準入力（`std::cin` や `_getch`）を通じた対話的な人間操作を前提としているため、**開発用AIアシスタントやCI/CDシステムによる「自動疎通テスト（ダミークライアントを用いた自動接続確認など）」を組み込むことが極めて困難**である。コマンドライン引数（CLI args）や環境変数を用いた初期化バイパス機構（例: `cccaster_v10.exe --host --port 10800 --headless`）が存在しないため、AIが自律的にテストスクリプトを走らせて通信品質を担保する仕組みの統合が妨げられている。

# main_app 構造および CLI UI リファクタリング詳細設計書

## 1. 概要
`src/app/main_app/` におけるユーザーコマンドラインインターフェース（CLI）の実装アーキテクチャについて、従来の「状態列挙（`AppState`）＋巨大な `switch` バケツリレー」から「インデックス駆動（データ駆動）型のメニューコールバック機構」へとリファクタリングを行いました。

本ドキュメントでは変更されたファイル群と、その関心・責務の分離について解説します。

---

## 2. 対象モジュールと責務

### `cccaster::main_app::controller::MainController`
* **責務**: アプリケーションライフサイクル全体の管理、および画面（ステート）間の遷移フロー制御。
* **アーキテクチャの変更点**:
  * **データ構造 `MenuOption` の導入**: 各画面の選択肢は文字列のラベルと `std::function<void()>` コールバックのペアを持つ `MenuOption` 構造体の配列として定義されます。
  * **分岐の排除**: 従来の `swtich (choice)` によるハードコードされた分岐処理を一掃し、「選択されたインデックスに対応する `MenuOption::onSelect` を直接呼び出す」ことで遷移およびアクションを実行します。
  * **階層の細分化**: より直感的なUIフローを実現するため、旧来の `NetplayConnection` 状態の手前に `NetplayHostOrClient` 状態を新設しました。これにより「プロトコルの選択」→「ホスト/クライアントの選択」→「対象ポートまたはIPの入力」という一貫したインデックスベースのメニューフローが形成されました。

### `cccaster::main_app::ui::ConsoleRenderer`
* **責務**: テキストベースのUI描画、ANSIエスケープシーケンスによる装飾、およびキーボード入力に基づくメニューカーソルの制御。
* **特徴**:
  * `DrawMenuAndGetSelection` 関数がUI描画と入力の要です。
  * 上下矢印キーによるインデックス選択、`Enter` による決定のほか、「`1`、`2` などの数字キーを押下することでダイレクトにそのインデックスの項目を決定する」機能を備えています。
  * 上記の `MainController` のインデックス駆動化と完璧に噛み合い、ロジックとビュー（描画）の分離を担保します。

### `cccaster::main_app::network_wrapper::SessionNegotiator`
* **責務**: ユーザーが入力した IP やポート番号のパース、およびゲームコア DLL への引き継ぎ前の UDP 穴開け（Punching）とレイテンシ測定。
* **変更点（関連）**: `MainController` 側で事前に関数 `ParseAddressAndPort` を呼び出す際、あらかじめホストかクライアントかを決定情報（`_isHost`）として保持しておくことで、パース処理とバリデーションをより単純明快に行えるようになりました。

## 3. なぜ「インデックス駆動」なのか
従来のハードコードされた `switch` 機構では、例えば「観戦モードの機能拡張で新しくメニュー項目を1つ追加したい」といった場合に以下のような修正波及が発生していました。
1. UI描画関数へ渡す文字列配列への要素追加
2. 列挙型 `enum AppState` への要素追加
3. `switch` 内の `case n:` 追加と、場合によっては後続の `case` 番号のズレの修正

`MenuOption` の配列を通じたデータ駆動型のアプローチでは、これら「選択肢」「処理」「遷移ロジック」が一つの要素として自己完結しているため、開発（AIおよび人間）による拡張が極めて安全かつ容易になります。

# ConfigManager (main_app) 詳細設計書

## 1. モジュール概要

* **機能**: INIライクな設定ファイル (`.ini` 等) の読み込み、保存、およびキー・バリュー形式での構造化データへのアクセスを提供する構成設定管理機能です。

## 2. 構造定義と責務

### `class Config`
* **概要**: インスタンス化して利用できる個別の設定オブジェクトを表現します。
* **ビジネス変数 (メンバ変数)**:
  * `std::unordered_map<std::string, std::unordered_map<std::string, std::string>> configData;`
    * セクション名（例: `[Network]`）をキーとし、その配下にあるパラメータ（例: `Port=10800`）のキーと値を保持する二重のハッシュマップです。

### `class ConfigManager`
* **概要**: グローバルにアクセス可能な静的（Static）な設定マネージャーです。
* **ビジネス変数 (静的メンバ変数)**:
  * `static std::unordered_map<std::string, std::unordered_map<std::string, std::string>> configData;`
    * `Config` クラスと同様の構造を持ちますが、アプリケーション全体で共有される単一の設定データを保持します。

## 3. 主要メソッド詳解

#### `Load(const std::string& filePath)`
* ファイルを開いて1行ずつ読み込みます。
* 先頭の余白を取り除く `Trim` 処理を行い、空行やコメント行（`;`, `#`）を除外します。

#### `Save(const std::string& filePath)`
* `configData` の内容を INI フォーマット（`[セクション名]` の下に `キー = 値`）で指定されたファイルパスに書き出します。

#### `GetString` / `GetInt`
* 指定されたセクションとキーに対応する値を取得します。
* データが存在しない場合やパース（`std::stoi` 等）に失敗した場合は、引数として提供された `defaultValue` を安全に返却します。

#### `SetString` / `SetInt`
* プログラム内からメモリ上の設定データ（`configData`）を更新・追加します。（ファイルへの永続化は `Save` 呼び出しが必要です）

# ConsoleRenderer (main_app) 詳細設計書

## 1. モジュール概要
* **ファイル**: `src/app/main_app/ui/ConsoleRenderer.cpp`, `src/include/cccaster/main_app/ui/ConsoleRenderer.hpp`
* **機能**: コマンドプロンプトやPowerShell等の標準入出力端末（CLI）に対してテキストを描画し、装飾（ANSIエスケープシーケンスによるカラーリングなど）とユーザーからのキー入力を処理するレンダリングエンジンおよび入力処理の責務を担います。

## 2. 構造定義と責務

### `class ConsoleRenderer`
* **機能**: 全てのメソッドが静的関数（`static`）として定義されたユーティリティクラスであり、アプリケーションのどこからでも画面描画と入力取得を行えるように設計されています。
* **ビジネス変数 (引数およびローカル)**:
  * `const std::string& title`: 画面上部に表示するUIとしての見出し。
  * `const std::vector<std::string>& options`: ユーザーに提示する選択肢のリスト。インデックス駆動アーキテクチャの根幹となる配列。
  * `bool allowCancel`: ユーザーが ESC キーを押下して「戻る」操作を行うことを許可するかどうかのフラグ。
  * `int selectedIndex`: ユーザーのキーボード入力（上下矢印）に基づいて現在強調表示されている選択肢のインデックスを保持する一時変数。

## 3. 主要メソッド詳解

#### `EnableVirtualTerminalProcessing()`
* Windowsコンソール（`cmd.exe`）において ANSI エスケープシーケンス（カラーコード等）をサポートさせるために `ENABLE_VIRTUAL_TERMINAL_PROCESSING` フラグを有効化します。

#### `ClearScreen()`
* OSに依存しないANSIのクリアではなく、フリッカー回避のために Windows ネイティブのAPI（`FillConsoleOutputCharacterA` 等）を使用して確実にターミナル画面全体をクリアします。

#### `DrawMenuAndGetSelection`
* TUI（Text User Interface）における基幹となるメニュー描画・操作取得ループです。
* **描画**: 引数 `title` と `options` を受け取り、`selectedIndex` と一致する要素だけ背景色（シアン等）を反転させてコンソールへ装飾出力を行います。
* **キー入力取得 (`_getch`)**:
  * 矢印キー（`UP`: `72`, `DOWN`: `80`）を解釈し、リストの範囲内で `selectedIndex` を循環（ラップアラウンド）させます。
  * **エンターキー (`\r` または `\n`)**: 決定として現在の `selectedIndex` を返却します。
  * **数字キー (`1`, `2`...)**: 表示されている順序に対応する数字キーが押された場合、ダイレクトに対象のインデックスを選択して返却します。
  * **ESCキー (`27`)**: `allowCancel` が真の場合、`-1` を返してキャンセル操作・階層戻りを表現します。

#### `PrintNetworkStatus`
* P2P セッション（UDP）確立後の通信状況を、現在行上書き（`\x1b[2K\r`）の手法を用いてリアルタイム描画します。
* 引数として受け取る `packetsReceived`, `packetsSent`, `currentPingMs` 等の情報に応じて、良好なら緑、遅延が大きい場合は赤といった動的カラーリングを適用します。

# MainController (main_app) 詳細設計書

## 1. モジュール概要
* **ファイル**: `src/app/main_app/controller/MainController.cpp`, `src/include/cccaster/main_app/controller/MainController.hpp`
* **機能**: CLI アプリケーション（ランチャー）のエントリーポイントとして機能し、ユーザーとのインタラクションフロー（メインメニュー、ネットプレイメニュー等）を管理・描画し、最終的にゲームプロセス（DLLフック等）の起動へと繋げます。

## 2. 構造定義と責務

### `enum class AppState`
* アプリケーションの現在地（状態）を示す列挙型です。
* `MainMenu`, `NetplayMenu`, `NetplayHostOrClient`, `NetplayConnection`, `Spectating_WaitingForHost`, `GameRunning`, `Exit` などの画面状態を定義します。

### `struct MenuOption`
* **ビジネス変数**:
  * `std::string label;`: 画面上に表示されるテキスト（選択肢の表示名）。
  * `std::function<void()> onSelect;`: ユーザーがこの機能を選択した際に発火するコールバック関数。状態遷移（`_currentState` の変更）やアクションを実行します。

### `class MainController`
* **ビジネス変数 (メンバ変数)**:
  * `AppState _currentState`: 現在の表示画面を示す状態変数（初期値は `MainMenu`）。
  * `bool _isIpv6`: ユーザーが IPv6 モードを選択したかどうかを保持するフラグ（初期値は `false`）。
  * `bool _isHost`: ユーザーがHost（ホスト）として待機するか、Client（クライアント）として接続するかを保持するフラグ（初期値は `false`）。

## 3. 主要フロー設計詳細

#### `void Run()`
* メインループです。`_currentState` が `AppState::Exit` になるまで継続してループし、現在の状態に対応する `HandleXXX()` メソッドへ処理を委譲します。

#### メニュー描画・遷移ハンドラ (`HandleMainMenu`, `HandleNetplayMenu`, `HandleNetplayHostOrClient`)
* `MenuOption` 構造体を用いて、表示すべき文字列とそれに対応するアクションを束ねます。
* 選択されたインデックスに対応する `MenuOption` 要素の `onSelect()` を直接実行する（データ駆動・インデックス駆動アーキテクチャ）ことで、ハードコードされた分岐を排除し拡張性を担保しています。
* **例**: IPv4を選択した場合は `_isIpv6 = false` とした上で `_currentState = NetplayHostOrClient` に遷移。

#### `HandleNetplayConnection()`
* 事前に決定された `_isIpv6` と `_isHost` のビジネス変数を参照し、コンソール上にホストまたはクライアント専用の手動IP/ポート入力プロンプトを構築します。
* 入力された情報（`std::string inputStr`）を `network_wrapper::SessionNegotiator::ParseAddressAndPort` に渡し、正当性の検証を行います。

#### `LaunchAndMonitorGame()`
* 事前準備（ネットプレイのネゴシエーション等）が完了した後に呼ばれます。
* **重要ビジネスロジック**: `SessionNegotiator` で一度確立し、通信品質（RTT等）を評価した一時的なUDPセッションをここで一旦閉じます。その後、`GameLauncher` （`cccaster::launcher`コンポーネント）を用いて `MBAA.exe` プロセスを起動し、先ほどロックインした**全く同じIPとポート番号を用いて**ゲームプロセス内部のDLLがHost/Clientとして通信を再開するよう引き継ぎを行います。

# main_app 実装における実務的不安材料 (10の懸念事項)

現在の `src/app/main_app` のソースコード（MainController, ConsoleRenderer, SessionNegotiator, ConfigManager 等）および設計ドキュメントをレビューした結果、将来的な運用や拡張においてクリティカルなバグやUX低下を招く恐れのある「実務的な不安材料（懸念点）」を10件抽出しました。

---

## 【アーキテクチャ・フローに関する不安材料】

### 1. 例外処理（Exception Handling）の欠如
**懸念**: `MainController::Run()` のメインループ内、および `MenuOption::onSelect` の呼び出しにおいて `try-catch` ブロックが存在しません。もし設定ファイルの読み込み時（`std::stoi` の例外など）やネットワークネゴシエーション時に予期せぬ C++ 例外がスローされた場合、CLIアプリケーション全体がクラッシュ（サイレント終了）し、ユーザーにエラー原因（「ポートが既に使用されている」等）が一切通知されません。

### 2. GameLauncher（ランチャー層）への戻り値ハンドリングと状態復帰
**懸念**: `LaunchAndMonitorGame()` でゲームのプロセスを起動（`monitor.BootAndMonitor`）した後、ゲーム側が正常終了・あるいはクラッシュ終了した際のハンドリングが不明瞭です。ゲームプロセスが死んだ後に直接 `MainMenu` へと遷移（`_currentState = AppState::MainMenu;`）していますが、この際「画面情報（バッファ）の完全な再初期化」や「確立していたネットワークの一旦切断処理（クリーンアップ）」が適切に行われているか不透明であり、2回連続で対戦しようとすると状態不整合を起こす危険性があります。

### 3. SessionNegotiator のソケット破棄タイミング
**懸念**: 「ネゴシエータで一度通信を確立・評価し、ゲーム（DLL）側で引き継ぐ」という設計ですが、`RunNegotiation` 関数を抜ける時点で `cccaster::network::UdpSocket socket` はローカル変数であるためデストラクタにより破棄されます。しかし、OSレベルでポートが完全に解放されるまでの遅延（TIME_WAIT等）により、直後に起動したゲームDLL側で同じポートをBindしようとした際に `WSAEADDRINUSE` （ポート使用中）エラーでバインドに失敗し、ゲーム内での通信が確立できない競合リスクが高いです（`SO_REUSEADDR` などの適用が必要か、あるいは OS への確実なポート返却保証が必要です）。

---

## 【UI/UX（コンソール描画）に関する不安材料】

### 4. ターミナルリサイズ時の描画崩れ
**懸念**: `ConsoleRenderer::DrawMenuAndGetSelection` や `PrintNetworkStatus` で画面をクリア・描画していますが、ユーザーが Windows のコマンドプロンプトのウィンドウサイズをマウスで変更した場合のリサイズイベントをハンドリングしていません。これにより、文字の折り返しが発生してレイアウトが激しく崩れたり、入力プロンプトが画面外に押し出されるリスクがあります。

### 5. std::getline と _getch() の併用による入力バッファの競合
**懸念**: メニュー移動には `conio.h` の `_getch()`（ブロックなし・即時キー取得）を使用していますが、IP/Port入力画面では `std::getline(std::cin)` （バッファリングあり）を使用しています。`_getch()` で処理されなかったエンターキーのキャリッジリターン（`\r` や `\n`）のゴミが `std::cin` のバッファに残っていた場合、`getline` 画面に遷移した瞬間に空文字として即座にスキップされ、元の画面に戻されてしまう「無限ループバグ」を引き起こす定石パターンの危険性があります（`cin.ignore` 等によるフラッシュ処理がありません）。

### 6. 入力キャンセル（ESC）の非統一な挙動
**懸念**: `DrawMenuAndGetSelection` では ESC キーで `-1` を返してキャンセルできますが、IP 直打ちプロンプト（`HandleNetplayConnection` 等）では `std::getline` で標準入力を待機している最中は ESC キーを押しても抜けられません。これにより「入力をやめて前の画面に戻りたい」ユーザーが強制的に無効な文字列を打って Enter を押すか、アプリごと閉じるしかなくなり、UXを著しく損ねています。

---

## 【ネットワーク・外部依存に関する不安材料】

### 7. 外部API (ipify.org) への依存とタイムアウト
**懸念**: `SessionNegotiator::GetGlobalIp` で WinINet（`InternetOpenUrlA`）を利用して自分自身のグローバルIPを取得していますが、これに対する明確なタイムアウト処理（あるいは非同期取得）が実装されていません。もし提供元のAPIサーバーがダウンしている場合、ホスト側は永遠に画面がフリーズしてしまい、メニュー操作に一切戻れなくなります。

### 8. 通信品質判定（Ping / Jitter）のアルゴリズムの脆弱性
**懸念**: `currentPingMs = currentPingMs * 0.8 + pingMs * 0.2;` のような 単純な指数移動平均 (EMA) でPingやジッターを計算していますが、通信開始直後の数パケットで極端なスパイク（500ms等）があった場合、その値がなかなか収束せず、実際は良好な回線であってもプレイヤーに「赤いPing表示」を見せ続けてしまうリスクがあります。極端な外れ値の除外（中央値ベースなど）が必要です。

---

## 【構造・モジュール管理に関する不安材料】

### 9. ConfigManager のスレッドセーフティ問題
**懸念**: `ConfigManager::configData` がグローバルな `static std::unordered_map` として実装されています。現在の `main_app` のフローは単純ですが、通信スレッド（SessionNegotiatorの受信コールバック内等）や今後のUIバックグラウンド更新などで複数のスレッドから同時に `GetInt` や `SetString` がコールされた場合、内部のハッシュマップ再配置によるアクセスクラッシュ（Segmentation Fault / Access Violation）が発生する危険性が非常に高いです。読み書きロック（ミューテックス）の実装が急務です。

### 10. MenuOption 寿命とキャプチャ変数のダングリング参照
**懸念**: `MainController` の `HandleXXX` の中で `std::vector<MenuOption> options` をローカル変数として構築し、ラムダ式に `[this]` をキャプチャさせています。現状は同期的に `options[choice].onSelect()` を即時評価（実行）するためセーフですが、将来的にUIの非同期化やアニメーション描画のために `MenuOption` を「メニューキュー」などに保持（遅延評価）する設計に変更した際、ローカル変数の寿命が切れて領域が破棄され、未定義動作（ダングリング参照クラッシュ）を招く、C++特有の落とし穴を孕んだ設計になっています。

# 実務的不安材料 (10の懸念事項) に対する対策案レポート

前回のレビューで抽出された10件の懸念事項に対して、具体的なソースコードの修正方針（対策案）を以下に定義します。

---

## 【アーキテクチャ・フローの修正】

### 1. 例外処理（Exception Handling）の欠如
**対策**: `MainController::Run()` のメインループ内、特に `options[choice].onSelect()` の呼び出し箇所を汎用的な `try-catch (const std::exception& e)` ブロックで囲みます。例外をキャッチした場合はエラーログをコンソールに出力し、ユーザーがキー入力（`_getch`）するまで待機させた上で、クラッシュさせずに `MainMenu` へと安全に回帰させるフェールセーフ機構を実装します。

### 2. GameLauncher への戻り値ハンドリングと状態復帰
**対策**: `LaunchAndMonitorGame()` メソッドにおいて、ゲームプロセス終了後（またはエラー終了後）の戻り状態を捕捉し、明示的にターミナルを初期状態へクリアします。また、再度ゲームをプレイしようとした際に前回のメモリや変数が残らないよう、必要なロジック変数（`_isIpv6` や `_isHost` などが必要なら）のリセット処理を挟むことで状態のクリーンアップを保証します。

### 3. SessionNegotiator のソケット破棄タイミング (WSAEADDRINUSE 対策)
**対策**: `SessionNegotiator::RunNegotiation` で使用している `cccaster::network::UdpSocket` に対して、OSがポートを即座に再利用できるようにするため `SO_REUSEADDR` ソケットオプションを明示的に有効化します（`UdpSocket` 側のコンストラクタや Bind 直後に設定するか、ネゴシエータ内で適切に Close されるよう破棄タイミングを制御します）。これにより、直後の DLL 側でのポートバインド競合を防止します。

---

## 【UI/UX（コンソール描画）の修正】

### 4. ターミナルリサイズ時の描画崩れ
**対策**: Windows専用の `SetConsoleWindowInfo` や `SetConsoleScreenBufferSize` などの API を `ConsoleRenderer::EnableVirtualTerminalProcessing()` やヘッダ出力時に呼び出し、コンソールのバッファサイズとウィンドウサイズをアプリケーション側で固定（例: 80x25 等）するか、リサイズ時に自動再描画されるフックを設けます。今回は最も確実かつ副作用の少ない「ウィンドウサイズとバッファを固定化してユーザー側でのリサイズを防止する」手法を導入します。

### 5. std::getline と _getch() の併用による入力バッファ競合
**対策**: `std::getline(std::cin, inputStr);` を呼び出す直前に、入力ストリームのゴミをフラッシュする処理（例: `std::cin.sync();` または直前でのキーボードバッファクリア）を挿入し、見えない改行コードによって入力が即座にスキップされる無限ループバグを防止します。

### 6. 入力キャンセル（ESC）の非統一な挙動
**対策**: IP・ポートを直接入力する画面において、ブロックを伴う `std::getline` の代わりに、非同期的に文字を１文字ずつ読み取る（`_kbhit()` と `_getch()` の組み合わせ）カスタムの行入力関数を `ConsoleRenderer` 側に新設します。この関数内で ESC キーが押された場合は空文字（またはキャンセルコード）を即座に返す設計とし、ユーザーがいつでも前のメニューへ戻れるように改善します。

---

## 【ネットワーク・外部依存の修正】

### 7. 外部API (ipify.org) への依存とタイムアウト
**対策**: `SessionNegotiator::GetGlobalIp` の `InternetOpenUrlA` 等の呼び出し時に、WinINet のオプション (`InternetSetOptionA`) を使用して、明示的な短いタイムアウト（例: 3〜5秒）を設定します。タイムアウトに達した場合やエラーが発生した場合はフリーズさせず、`"Unknown IP (API Timeout)"` 等の代替文字列を返却して進行を妨げないようにします。

### 8. 通信品質判定（Ping / Jitter）のアルゴリズム改善
**対策**: Ping値の計算（EMA: 指数移動平均）において、単純な `0.8 : 0.2` の加重平均だけでなく、「前回と今回の差分が100msを超えるような極端な値（スパイク）は、連続してパケットロス等がない限り一時的なものとして除外・または平滑化の重みを極端に下げる」などのアウトライア（外れ値）フィルタリング処理を論理に追加します。

---

## 【構造・モジュール管理の修正】

### 9. ConfigManager のスレッドセーフティ対応
**対策**: `src/include/cccaster/main_app/ConfigManager.hpp` の `ConfigManager` および `Config` クラスに `<shared_mutex>` (C++17) を導入し、静的変数 `configData` へのアクセスを保護します。`GetString` などの Read 操作には `std::shared_lock` (複数同時読み取り許可)、`SetString` などの Write 操作には `std::unique_lock` (排他書き込み) を適用し、通信スレッドからの同時参照によるクラッシュリスクを完全に排除します。

### 10. MenuOption 寿命とキャプチャ変数のダングリング参照回避
**対策**: 現在の同期実行ループにおいては `this` キャプチャでも直ちに問題は起きませんが、アーキテクチャの堅牢性を高めるため、キャプチャを明示的なポインタ渡しによる安全性アサートにするか、`MenuOption` を動的アロケーション（または `MainController` クラスメソッドへの関数ポインタ）に改めて寿命を明示化し、未定義動作のリスクをドキュメント上（または実装上）で封じ込めます。

# メモリスナップショットによる瞬間高速起動（Warp FastBoot）設計書
	
## 1. 概要と目的
本機能は、既存の「入力をスキップさせて目的の画面まで自動進行する」アプローチ（`GameLauncher`）からさらに一歩進め、**目的の画面（キャラクターセレクトやバーサスモード）のプロセスメモリ状態を丸ごとキャプチャしてファイルに保存し、次回起動時にそのメモリ差分を直接流し込む（LoadState）ことで、起動直後から数ミリ秒で目的の画面へワープ（瞬間移動）させる**究極の起動高速化を実現するための計画です。

## 2. 実装方針と段階的アプローチ

### フェーズ1: フルメモリスナップショットによる概念検証（PoC）
まずは差分（Diff）計算を行わず、メモリ空間全体を直接上書きするアプローチで動作証明（LoadStateの成功可否）を行います。

**キャプチャ手順 (SaveState)**
1. ゲーム起動
2. 通常の手段（手動またはGameLauncher）で「キャラクターセレクト画面」まで進める
3. **ゲームを一時停止（SuspendThread）**
4. ゲームプロセスのRW（Read/Write）可能なメモリ領域をすべて読み取る
5. 取得した全メモリダンプをバイナリファイル（例: `bin/states/char_select.bin`）として保存

**ロード手順 (LoadState)**
1. ゲーム起動（初期化直後の段階）
2. **ゲームを一時停止（SuspendThread）**
3. 保存しておいた全メモリダンプ (`char_select.bin`) をゲームプロセスの該当アドレスへ丸ごと上書き（WriteProcessMemory）
4. **ゲーム一時停止解除（ResumeThread）**
5. 正常にキャラクターセレクト画面が描画・操作できるかを検証する。

### フェーズ2: さらに深い階層（バーサスモード）への適用
フェーズ1の「起動直後 -> キャラセレ」へのワープが成功した場合、同様の手順で「バーサスモード（試合開始直前）」の全メモリダンプ（例: `bin/states/versus_mode.bin`）を作成し、起動直後から一気に試合画面までワープできるかを検証します。

### フェーズ3: メモリ差分（Diff）による最適化
フルメモリダンプはファイルサイズが大きくなり、またOSや環境依存のポインタ（ヒープ・スタック等）まで上書きしてクラッシュを引き起こすリスクがあります。そのため、正常動作が確認できた後は「差分適用方式」へ移行します。

1. **起動直後（初期状態）** の全メモリをキャプチャしてハッシュ/ベースラインを保持。
2. キャラクターセレクト画面まで進んだ後、再度メモリをキャプチャ。
3. **初期状態とキャラセレ状態のメモリ差分（変更されたアドレスとデータのみ）**を抽出し、パッチリスト（ポインタと値のペア群）として保存（例: `bin/states/char_select.patch`）。
4. 以降のLoadStateでは、ゲーム起動・一時停止後、このパッチリストに記載されたアドレスのみを上書き適用し、ワープを実行する。

---

## 3. 保存・ロードの対象と構成
ディレクトリ構造:
```text
build/
  └── bin/
       ├── CCCaster_v10.exe
       ├── libcccaster_hook.dll
       └── states/                  <-- 新設（スナップショット保存用）
            ├── base_init.bin       (初期状態スナップショット)
            ├── char_select.patch   (キャラセレへの差分パッチ)
            └── versus_mode.patch   (バーサスへの差分パッチ)
```

## 4. 懸念事項と技術的課題
1. **ASLR (Address Space Layout Randomization) の影響**
   - MBAACCがASLR有効でコンパイルされている場合、起動ごとにベースアドレスが変わるため、絶対アドレスでの保存・復元はクラッシュを招きます。常にベースアドレスからの「相対オフセット」として差分を管理する必要があります。
2. **ヒープポインタの再利用**
   - オブジェクトの動的確保（ヒープ領域）やスタックフレームのズレがある場合、メモリをそのまま戻してもポインタの指し示す先が不正になりアクセス違反（Access Violation）が起きる確率が高いです。
   - もしフルダンプ復元でクラッシュする場合、「静的メモリ領域（.data / .bss セクション）」のみをスナップショット対象に絞るか、状態復元用の関数を直接CallするGGPO（ロールバック）的な同期手法に頼る必要があります。
3. **デバイス・リソース状態の乖離**
   - メモリの状態だけを未来に進めても、DirectX（テクスチャやサーフェス）やDirectSoundの初期化状態・VRAM内のリソースが付いてこず、画面が真っ暗になる、あるいは音が鳴らないなどの現象が起きる可能性があります。
