# 効果音API内訳と初観測Playの遅延

## 実装と4人の独立調査

ユーザーの明示依頼により4人のサブエージェントで、ゲーム逆アセンブル、既存計測・ETW、Windows音声構成、実装と生ログの独立検算を担当。実機起動とコード統合は親が順次実行した。

`CCCASTER_SOUND_API_PROBE=1` はSoundProbeも有効化する診断専用スイッチ。通常動作では無効。
SFXテーブルから生成済み274バッファのvtableを取得し、各実装のGetStatus/Stop/SetCurrentPosition/SetVolume/SetPan/Play、およびLock/Unlock/Restoreをフック。
stdCallの引数と戻り値を保存し、対象ゲームスレッドのSoundUpdate内だけを固定長2048件へ採取。開始終了QPC、バッファ、音番号、呼出元、引数、HRESULT/status、親通番、再計算、ネスト深度を記録。
数値の整形は次のPresent。設置・探索は計測前で、最初の親区間をwarmupとして除外する。初回発見後に異なるvtable実装が生成されるケースは未確認。
`analyze_sound_api.py` は同Fの再計算も親通番で区別し、API区間の和集合を親時間から引く。残余には走査・フック費用も含む。

## Windows側の経路

両プロセスはMicrosoft標準32bit dsound.dll 10.0.26100.9278、AudioSes/MMDevAPIを使用。ゲームフォルダーにALchemy等のdsound置換なし。
Play RVA0x33990は共通mutexのWaitForMultipleObjectsを呼び、末尾でReleaseMutex。
内部の資源準備候補RVA0x2EFC0はobject+0x58のbit0x80を検査し、未設定時に追加処理、設定済みなら早期成功。RVA0x32643がこのbitを設定する。
この分岐は初観測Playの差に整合するが、内部関数の所要時間や資源内容の実帰属は未達。
根拠は `build_logs/dsound_32_disassembly_20260911.txt`、`dsound_32_pe_20260911.txt`。公開PDBはHTTP503で取得できなかった。

共有mutexの実測にはDirectSoundのPE importから実IATターゲットを解決し、WaitForMultipleObjectsをネスト採取する。
Kernel32の通常エクスポートを捕捉した071633では待機行を取得できなかったため、同試行を待機0の根拠にしない。

## 試験環境の新規不具合

PowerShell7.6.6で `[Environment]::SetEnvironmentVariable(name,$null,'Process')` が空文字を子へ継承し、C++のgetenv判定が真になった。
そのため過去065940には、解除予定のRenderApi/DisplayPaceログが残っていた。
run_spin_etwの解除と未定義状態への復元をRemove-Item Env:へ修正。これは測定負荷の混入原因であり、過去の音169.7µsの直接原因だとは断定しない。

## 今後の対策候補

優先対象は未使用バッファの初回再生準備を戦闘のクリティカルな区間から外すこと。無音での事前再生等は、元のバッファ・音量・位置・ループ・再ヒットの意味を保てるか別途検証が必要。
SetCurrentPositionやPlayを安易に省くと再ヒット音が変わるので、本変更では音の意味を変える最適化は入れていない。
個別APIの経過時間はCPU処理だけを意味せず、未観測の停止も含む。Creativeドライバが今回の遅延源だとの証拠はない。
